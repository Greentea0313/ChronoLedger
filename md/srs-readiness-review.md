# SRS 작성 및 설계 단계 진입 검토

> 상태: **초기 검토 이력**. 당시 SRS 작성 보류 결론은 사용자 결정 보완 전 상태다. 후속 초안은 [SRS.md](SRS.md)를 참조한다. 승인 및 SQL 실행 검증 전까지 설계 진입 게이트는 계속 열린 상태다.

- 검토일: 2026-10-02
- 범위: `md/revisions_and_decisions.md`, `md/SPEC.md`, `md/SCHEMA.sql`, `docs/to-do.md`, `docs/architecture.md`
- 결과: **기획 오류/누락 있음. 조건부 SRS는 작성하지 않음. 설계 단계 공식 진입은 보류.**
- 검증 방식: 문서 및 SQL 정적 검토. PostgreSQL/Supabase 실행과 자동 테스트는 하지 않음.

## 결론

기능 방향과 주요 결정은 상당히 구체화되어 있지만, 요구사항과 DDL/RLS 사이에 구현 동작을 바꾸는 불일치가 남아 있다. 사용자의 조건은 “기획에 오류가 없다면 SRS 작성”이므로 이 상태에서 확정 SRS를 작성하지 않았다. 현재 `md/SPEC.md`는 간략한 기능·화면 요약이며, 요구사항 식별자와 검증 가능한 수용 기준을 가진 SRS를 대신하지 못한다.

세부 UI 탐색이나 기술 대안 검토는 시작할 수 있지만, **요구사항 베이스라인 승인 및 상세 설계 착수 게이트는 통과하지 못했다.** 아래 P0/P1 항목을 정리하고 SRS를 검토·승인한 뒤 설계 기준을 동결하는 것을 권고한다.

## 설계 진입을 막는 항목

### P0 — 구독 예정 지출의 취소·삭제 상태 전이

`md/SCHEMA.sql`의 예정 지출 UPDATE 정책은 `USING`과 `WITH CHECK` 모두 `status = 'PLANNED'`를 요구한다(664–669행). 따라서 사용자가 예정 지출을 `CANCELLED`로 바꿀 수 없다. 반면 DELETE 정책은 모든 본인 `PLANNED` 항목을 삭제할 수 있어 구독 생성 항목도 삭제할 수 있다(670–671행). 이는 취소 회차를 보존해 자동 재생성을 막는 요구와 반대다. 유일 인덱스는 취소 회차까지 남기므로 현재 상태에서는 재예정할 RPC도 없다.

**결정/수정 필요:** `PLANNED → CANCELLED`를 허용하는 제한된 경로를 만들고 구독 생성 지출의 직접 DELETE를 차단한다. 취소 후 재예정은 같은 회차를 되돌릴지, 별도 이력/회차를 만들지 제품 동작을 확정하고 RPC·멱등 인덱스와 함께 설계한다.

### P1 — Google Play 적립 기준의 공식성 및 계산 기준

마스터 명세와 SQL은 Google 공식 등급별 적립률을 적용한다고 선언하고 `ROUND(final_amount * rate / 100)`으로 계산한다(`md/revisions_and_decisions.md` 2.2절, `md/SCHEMA.sql` 304–306행). Google 도움말은 상품 가격을 기준으로 적립하고 세금은 제외한다고 설명하며, 가까운 정수로 반올림하는 예를 제시한다. 현재 앱 데이터에는 세금 또는 Google 적립 대상 금액 필드가 없고 `final_amount`는 일반 할인과 포인트 할인을 모두 뺀 금액이다. 따라서 이 식이 Google의 실제 적립액을 재현하는지, 앱 내부 예측 규칙인지 구분해야 한다.

**결정/수정 필요:** 세금 제외 기준과 포인트 할인·쿠폰 사용 시 적립 대상 금액을 확정한다. 실제 정산액이 아닌 추정치라면 UI와 요구사항에 “예상 적립”으로 표시한다. 공식 등급별 비율은 한국 Google Play 도움말을 기준으로 유지한다. [Google Play 포인트 적립 계산 안내](https://support.google.com/googleplay/answer/9077192?co=GENIE.CountryCode%3DKR&hl=ko-KR)

### P1 — 지출 생성 시 참조 데이터 소유권/일관성

지출 INSERT 정책은 사용자 ID, 예정 상태, 포인트 수치만 검사한다(`md/SCHEMA.sql` 665–666행). FK 유효성만으로는 `template_id`가 그 사용자의 구독 템플릿인지, `schedule_id`가 `game_id`와 같은 게임의 일정인지, 해당 게임이 사용자 선택과 일치하는지 보장되지 않는다. 다른 사용자의 템플릿 UUID를 참조하면 구독 회차 유일 인덱스를 선점해 실제 템플릿 생성에 영향을 줄 수 있다.

**결정/수정 필요:** 예정 지출 생성/수정 RPC 또는 DB 트리거에서 템플릿 소유권, 일정-게임 일치, 필요한 경우 사용자 게임 구독 관계를 검증한다. 직접 쓰기를 유지할 경우에도 같은 불변식을 강제한다.

### P1 — 만료된 일정 연결 예정 지출의 수명주기

체크리스트는 “만료 처리”를 요구하지만(마스터 명세 7.2절), 지출 상태에는 `PLANNED`, `CONFIRMED`, `CANCELLED`만 있고 일정 종료 후 미결제 건을 어떻게 처리하는지 정해져 있지 않다. 자동 취소, 계속 예정으로 유지, 사용자 확인 후 취소/일정 이동 중 어떤 동작인지 불명확하다.

**결정 필요:** 기간 종료 후 알림 시점, 예산 귀속, 편집/결제 허용 여부, 취소 상태 전환 및 재예정 규칙을 정의한다. 기존 세 상태만으로 표현한다면 어떤 상태 전이를 쓸지 명시한다.

### P1 — 신규 사용자 재정 초기화와 첫 사용 조건

`process_expense_payment`는 자산 차감이 선택되면 `user_finances` 행이 없을 때 실패한다(`md/SCHEMA.sql` 318–324행). 별도의 `set_user_finance_settings` RPC는 있으나 가입 직후 호출 시점, 기본 예산/자산 초기값, 초기화가 안 된 상태에서 캘린더·지출 등록을 허용할지 요구사항과 가입 흐름에 연결되어 있지 않다.

**결정 필요:** 가입/첫 로그인/첫 결제 중 초기화 시점과 기본값을 정하고, 실패·중복 호출의 동작을 요구사항에 적는다. DB trigger 또는 클라이언트 온보딩 중 어느 방식인지 설계 단계에서 결정한다.

## SRS 완성에 필요한 추가 명세

- 각 요구사항에 `FR-`, `NFR-`, `SEC-` 등 고유 ID와 우선순위를 부여하고, 검증 가능한 수용 기준을 연결한다.
- 계산·날짜 규칙을 확정한다: KST 기준일, 월 경계, Google 포인트 산정 기준, 포인트·금액 반올림, 0원 결제, 날짜 소급 입력.
- 상태 모델을 표로 정의한다: 지출 상태 전이, 구독 회차 재예정, 일정 요청/게임 요청 상태, 종료된 일정의 미결제 지출 처리.
- 역할별 권한 행렬을 작성한다: 비인증 사용자, 일반 사용자, 관리자, 서버/RPC. 각 엔티티별 CRUD와 승인 범위를 기록한다.
- 비기능 요구사항을 정량화하거나 명시적으로 범위에서 제외한다: 개인정보 캐시 보호/삭제, 인증 세션 만료, 백업·복구, 가용성, 접근성, 지원 브라우저/OS, 성능 목표, 로그·감사 보존.
- 외부 서비스 경계와 실패 동작을 정의한다: Supabase Auth/OAuth·Storage·PostgreSQL, Tauri 딥링크, 오프라인 캐시, 네트워크 단절 중 진행 중인 작업.
- UI 요구사항에 화면별 입력·검증·빈 상태·오류 메시지·위험 작업 확인을 포함하고, 데이터 모델 및 요구사항으로 추적 가능하게 한다.
- 원문의 `[cite: n]` 참조 ID가 프로젝트 내 출처 목록과 연결되지 않는다. 추적 가능한 참고문헌/결정 로그로 정리한다.

## 설계 단계 진입 판정

| 게이트 | 판정 | 근거 |
|---|---|---|
| 제품 범위와 핵심 사용자 흐름 | 조건부 통과 | 핵심 화면·결제·일정 흐름은 있으나 만료/재예정/온보딩 일부 미정 |
| 요구사항 간 모순 없음 | 미통과 | 취소·삭제 RLS가 구독 회차 정책과 충돌 |
| 회계 규칙 검증 가능성 | 미통과 | 공식 적립액 산정 기준과 앱 계산 기준이 같다고 확인되지 않음 |
| 권한·데이터 불변식 | 미통과 | 지출 참조 데이터 소유권/관계 검증이 명세에서 빠짐 |
| 요구사항 추적성과 수용 기준 | 미통과 | 현 `SPEC.md`에는 식별자·수용 기준·요구사항 추적표가 없음 |
| SQL 실행 검증 | 미실시 | 이 검토는 정적 검토만 수행 |

**최종 판정:** SRS 확정 전에는 상세 설계 기준선을 승인하지 않는다. 위 P0/P1 항목과 SRS 요구사항을 닫은 뒤 추적성 검토 및 핵심 시나리오 리뷰를 통과하면 설계 단계로 공식 전환할 수 있다. 데이터베이스 초안 정적 검토 또는 UI 와이어프레임 같은 탐색 작업은 병행 가능하되, 미확정 규칙은 설계 입력으로 고정하지 않는다.

## 이번 검토 범위 밖

- SQL 구문이 실제 Supabase 버전/권한 구성에서 실행되는지 확인하지 않았다.
- Google Play 등급별 비율과 공식 계산 안내는 공식 도움말을 확인했지만, 실제 Play 결제별 세금·쿠폰 적용 결과와 앱 모델의 정합성은 별도 테스트하지 않았다.
- 코드, 테스트 스위트, 배포 설정은 존재 여부를 검증하거나 실행하지 않았다.
