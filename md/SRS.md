# ChronoLedger 소프트웨어 요구사항 명세서 (SRS)

- 버전: 1.0
- 작성일: 2026-10-02
- 상태: 사용자 요구사항 승인 및 SQL 스모크 검증 완료, 설계 단계 진입 승인
- 기준 문서: [통합 기획 및 결정](revisions_and_decisions.md), [기능 명세](SPEC.md), [차단 항목 결정](resolved-blockers.md), [DB 스키마 초안](SCHEMA.sql)

## 1. 목적과 범위

ChronoLedger는 게임 일정과 개인 지출 계획을 연결하고, 정기 구독·스토어 포인트·예산을 관리하는 개인용 앱이다. 하나의 Next.js 코드베이스에서 Windows용 Tauri v2 데스크톱 실행 파일과 Android용 모바일 PWA를 제공한다. 인증, 데이터베이스, 파일 저장은 Supabase Auth, PostgreSQL, Storage를 사용한다.

이 문서는 승인된 요구사항과 수용 기준을 정의한다. 구현 상세 및 실제 배포 구성은 포함하지 않는다. 사용자가 요구사항을 승인했고 테스트 프로젝트에서 rollback-only SQL 스모크 검증을 완료해 설계 단계 진입이 승인됐다.

### 1.1 범위 내

- 인증된 사용자의 자산, 월 예산, 게임 일정 구독, 지출, 메모 및 스토어 포인트 관리
- VERSION/PICKUP 일정 조회와 일정 연계 지출 계획
- 정기 구독 지출의 멱등 생성
- 결제 확정, 예정 지출 취소·복구, 결제 환불
- 온라인 및 인증 세션 유효 상태의 오프라인 캐시 조회
- 관리자에 의한 공용 게임/일정 관리 및 사용자 제안 승인

### 1.2 범위 밖

- 금융기관 계좌 연동, 자동 결제 및 실제 스토어 결제 검증
- Google/Galaxy 스토어 서버 정산 결과 동기화
- 서버 크론 기반 반복 지출 생성
- 일반 이벤트/점검 일정, 인게임 상품 카탈로그

## 2. 사용자와 권한

| 역할 | 권한 |
|---|---|
| 일반 사용자 | 본인 계정 및 재무·지출·메모·구독 템플릿 관리, 공용 일정 조회, 게임/일정 제안, 결제 및 환불 RPC 호출 |
| 관리자 | 일반 사용자 권한에 더해 공용 게임/일정의 직접 관리, 요청 승인·반려 |
| 비인증 사용자 | 개인 데이터 및 캐시 접근 불가 |

관리자 역할은 서버가 관리하는 JWT `app_metadata.role=admin`에서 판정한다. 클라이언트가 권한을 부여할 수 없어야 한다. 모든 개인 레코드는 RLS로 소유자 격리한다. 지갑 잔액, 포인트 원장, 확정 지출 및 자산 변화는 검증된 RPC 경로로만 변경한다.

## 3. 용어와 날짜 규칙

- **예정 지출**: `PLANNED` 상태의 지출.
- **확정 지출**: 결제 기록이 완료된 `CONFIRMED` 상태의 지출.
- **예정 취소**: 결제 전 사용자가 취소한 `CANCELLED` 지출. `cancellation_kind=PLANNED_CANCEL`.
- **환불**: 확정 결제를 되돌린 `CANCELLED` 지출. `cancellation_kind=PAYMENT_REFUND`.
- **KST 오늘**: `Asia/Seoul` 시간대의 현재 날짜. 기한 및 미래 결제 날짜 비교에 사용한다.
- 모든 통화 금액은 KRW 정수로 저장한다. 포인트 수량도 정수로 저장한다.
- 예산 월 귀속은 `CONFIRMED`의 `target_date` 월, `PLANNED`의 일정 종료일(`end_date`) 또는 `target_date` 월, `CANCELLED` 제외를 기본으로 한다.

## 4. 기능 요구사항

### 4.1 가입 및 초기 데이터

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| FR-001 | 신규 인증 계정 생성 시 재무 기본값과 두 스토어 지갑을 자동 생성해야 한다. 별도 온보딩은 요구하지 않는다. | 가입 완료 후 `user_finances`에 사용자별 1행(자산 0, 기본 예산 0), Google 지갑 1행(잔액 0, BRONZE, 적립률 0.10), Galaxy 지갑 1행(잔액 0, 적립률 0.10)이 존재한다. 초기화는 재시도해도 중복 행을 만들지 않는다. |
| FR-002 | 월별 예산이 없거나 월별 예산 금액이 0원이면 기본 예산을 적용해야 한다. | 양수인 월별 예산만 `default_budget`을 덮어쓴다. 월별 예산 행이 없거나 금액이 0원이면 `default_budget`을 사용한다. 가입 시 당월 `monthly_budgets` 행을 반드시 생성하지 않는다. 최종 적용 예산이 0원이면 비율 경고와 초과 확인을 표시하지 않는다. |
| FR-003 | 사용자가 본인 계정 삭제를 요청하면 해당 계정의 개인 데이터를 삭제해야 한다. | 삭제 완료 시 재무, 예산, 게임 구독(`user_games`), 구독 템플릿, 스토어 지갑, 메모, 지출, 포인트 원장, 게임/일정 제안 및 해당 사용자의 비공개 아이콘을 삭제한다. 공용 게임/일정은 유지한다. 권한이 있는 서버 측 경로에서 본인 계정 삭제만 수행하며, 완료 안내 전 개인 Storage 객체까지 정리한다. 개별 지출 물리 삭제 금지는 계정 유지 중의 규칙이며 계정 전체 삭제에는 적용하지 않는다. |
| FR-004 | 사용자는 총 자산, 기본 예산 및 월별 예산을 수정할 수 있어야 한다. | 총 자산은 음수를 허용하고 기본/월별 예산은 0 이상의 정수 KRW만 허용한다. 월별 예산 행이 없으면 기본 예산을 적용한다. 변경은 인증 사용자 전용 검증 경로로 반영된다. |
| FR-005 | 사용자는 이메일 가입/로그인 또는 Google OAuth로 인증할 수 있어야 한다. | 로그아웃 또는 세션 만료 후 개인 데이터와 캐시를 표시하지 않는다. Tauri에서 Google 인증을 시작하면 deep link callback으로 앱에 세션을 전달한다. 비인증 상태에서 개인 기능은 사용할 수 없다. |

### 4.2 일정·게임 및 제안

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| FR-010 | 공용 일정 종류는 `VERSION`, `PICKUP`만 지원한다. | 등록/수정/요청에서 다른 종류는 거부된다. 종료일은 시작일보다 빠를 수 없다. |
| FR-011 | 일반 사용자의 게임/일정 추가 및 수정 제안은 요청 레코드로 저장하고 관리자 승인 후 공용 데이터에 반영한다. | 요청 상태 전환과 카탈로그/일정 반영은 원자적이다. 게임 승인만으로 요청자 `user_games` 등록을 자동 생성하지 않는다. |
| FR-012 | 관리자가 일정 날짜를 바꾸면 연결된 예정 지출 날짜를 동기화해야 한다. | 연결된 `PLANNED` 지출의 일정 시작일·종료일·목표일이 새 일정에 맞춰 갱신되고, `CONFIRMED` 지출의 결제 기록은 유지된다. |

### 4.3 캘린더·예산

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| FR-020 | 캘린더 타일은 금액이나 일반 지출 목록을 표시하지 않는다. | 타일에는 게임 아이콘, 일정 배너, 개인 메모 도트만 표시된다. 상세는 데스크톱 사이드바 또는 모바일 바텀 시트에서 조회한다. |
| FR-021 | 일정 연결 예정 지출은 일정 종료일이 속한 월 예산에, 확정 지출은 결제일이 속한 월에 귀속한다. | 화면·경고·집계는 동일한 귀속 규칙을 쓰며 취소 항목은 제외한다. 확정 지출은 `deduct_from_asset` 설정과 관계없이 소비 통계에 포함한다. |
| FR-022 | 적용 예산이 0원보다 클 때 월 예상 소비액이 예산의 80%에 도달하면 주의, 100%를 초과하면 위험 표시를 제공해야 한다. | 등록/조회 결과의 월 예상 소비액에 따라 경고가 재계산된다. 변경으로 월 예상액이 증가해 100%를 넘으면 저장/확정 전에 최종 확인한다. 적용 예산이 0원이면 비율 경고와 초과 확인을 생략한다. |

### 4.4 지출 상태 및 권한

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| FR-030 | 계정이 유지되는 동안 사용자 지출 행은 개별 물리 삭제하지 않는다. 예정 지출 수정은 본인 소유의 `PLANNED` 행에서만 허용한다. | 사용자 DELETE는 RLS/권한으로 거부된다. 확정/취소 행 직접 수정은 허용되지 않는다. 계정 삭제 요청 완료 시의 개인 데이터 삭제는 FR-003 예외를 따른다. |
| FR-031 | 사용자의 예정 취소는 전용 RPC로 `PLANNED → CANCELLED` 처리하고 취소 원인을 기록한다. UI 액션명은 “예정 취소”여야 한다. | 소유자 본인의 예정 행만 `PLANNED_CANCEL`로 변경된다. 취소 행은 예산 집계에서 제외되며 반복 생성 대상이 되지 않는다. |
| FR-032 | 복구 가능한 예정 취소 지출은 복구 RPC로 `CANCELLED → PLANNED` 전환할 수 있다. | `PLANNED_CANCEL`은 복구할 수 있다. `TEMPLATE_DEACTIVATION`은 소유 템플릿이 활성화된 경우에만 복구할 수 있다. `PAYMENT_REFUND` 행 복구 요청은 거부된다. 복구 시 기존 날짜를 보존하고 예산 집계에 포함한다. 기존 `target_date`가 KST 오늘보다 과거면 만료 항목 모달에 다시 포함한다. |
| FR-033 | 예정 지출의 모든 참조 관계를 데이터베이스에서 검증해야 한다. | `schedule_id`가 있으면 지출 `game_id`가 일정 `game_id`와 일치해야 한다. `template_id`가 있으면 템플릿 소유자가 지출 소유자와 같아야 하며, 양쪽 게임 ID가 있으면 일치해야 한다. 불일치 INSERT/UPDATE는 거부된다. |

### 4.5 결제·포인트·환불

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| FR-040 | 결제 확정은 서버 RPC가 금액과 소유권을 검증하고 지출, 자산, 포인트 잔액·원장을 원자적으로 갱신해야 한다. | `final_amount = original_price - discount_amount - point_discount_amount`이며 모든 입력 할인은 0 이상이고 실결제액은 음수가 될 수 없다. 실패 시 전체 변경이 롤백된다. 지원 결제수단은 WALLET, GOOGLE_PLAY, GALAXY_STORE다. 미래 KST 날짜 결제는 거부한다. `deduct_from_asset=true`면 `final_amount`를 총 자산에서 차감하고 환불 시 되돌린다. 오늘 결제는 기본 켬, 과거 내역은 기본 끔이며 사용자가 변경할 수 있다. |
| FR-041 | 포인트 사용 수량(P)과 포인트 할인 금액(KRW)은 별도 입력 및 저장한다. | 둘 다 0이거나 둘 다 양수인 일치 조건을 검증하며, 선택한 포인트 지갑 잔액보다 많이 사용할 수 없다. Google/Galaxy Store 결제면 포인트 플랫폼은 결제 스토어와 같아야 한다. WALLET 결제는 사용 포인트 플랫폼을 별도로 선택할 수 있다. |
| FR-042 | 포인트 적립은 실제 결제수단으로 선택한 스토어의 적립률을 이용한 앱 예상치로 계산한다. | 결제수단이 Google Play 또는 Galaxy Store일 때만 `earned_points = floor(final_amount × selected_store_earn_rate / 100)`을 서버에서 계산해 해당 지갑에 가산하고 `EARN` 원장에 남긴다. WALLET 결제는 스토어 포인트 사용 여부와 관계없이 적립하지 않는다. 사용자 UI/문서에서 공식 정산 보장으로 표현하지 않는다. |
| FR-043 | 사용자는 지갑 잔액을 목표 잔액으로 수동 보정할 수 있어야 한다. | 보정 RPC는 잔액을 음수로 만들지 않으며 실제 변경분을 `MANUAL_ADJUST` 원장에 기록한다. |
| FR-044 | 확정 결제 환불은 별도 RPC에서 자산과 사용 포인트를 복원하고 지출을 `PAYMENT_REFUND`로 취소해야 한다. | 적립 포인트 회수 후 잔액이 음수가 되면 환불 전체가 롤백된다. 자동 적립/사용을 되돌리며, 독립적인 수동 보정 원장 행은 환불이 변경하지 않는다. |
| FR-045 | 사용자는 스토어 지갑의 적립 설정을 변경할 수 있어야 한다. | Google Play는 BRONZE 0.10%, SILVER 0.11%, GOLD 0.13%, PLATINUM 0.16%, DIAMOND 0.20%만 허용한다. Galaxy Store는 0~100% 범위에서 사용자가 적립률을 설정한다. 변경은 이후 결제 적립 계산에 적용하고 과거 지출의 저장된 적립량은 바꾸지 않는다. |

### 4.6 정기 구독

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| FR-050 | 활성 구독 템플릿의 당월 지출은 캘린더 진입 시 지연 생성한다. | `(template_id,billing_cycle)` 유일성으로 반복 호출/동시 실행에도 월별 행은 최대 1개다. 취소된 회차는 같은 달에 자동 재생성하지 않는다. 비활성 템플릿은 새 회차를 생성하지 않는다. |
| FR-051 | 결제일이 해당 월의 일수보다 크면 말일로 보정한다. | 예: 31일은 평년 2월 28일, 윤년 2월 29일, 4월 30일로 생성한다. |
| FR-052 | 사용자가 구독 템플릿을 비활성화하면 이미 생성된 해당 템플릿의 미결제 예정 지출을 취소해야 한다. | 연결된 모든 `PLANNED` 행은 물리 삭제하지 않고 `CANCELLED/TEMPLATE_DEACTIVATION`으로 전환한다. 재활성화는 향후 회차 생성만 재개하며 취소 회차를 자동 복구하지 않는다. 해당 회차는 FR-032에 따라 명시적으로 복구할 수 있다. |
| FR-053 | 구독 템플릿의 물리 삭제는 허용하지 않는다. | 사용자는 템플릿을 조회·추가·수정할 수 있지만 DELETE 요청은 거부된다. 반복 결제 종료는 비활성화로 수행한다. |

### 4.7 만료된 예정 지출과 오프라인

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| FR-060 | 만료 항목은 모든 `PLANNED` 지출 중 `target_date < KST 오늘`인 행이다. 시스템은 자동 취소하지 않는다. | 온라인 캘린더 진입/복귀 때 미처리 항목을 조회한다. 항목은 해결 전까지 예정 소비 추정에 남는다. |
| FR-061 | 온라인에서는 미해결 만료 항목별 결제 확정, 예정 취소, 가능한 다음 일정 이동 중 하나를 선택해야 인터랙티브 캘린더를 계속 사용할 수 있다. | 모든 미해결 항목을 처리하기 전에는 온라인 모달을 닫아 정상 조작을 계속할 수 없다. 서버 상태를 다시 조회해 잔여 항목을 갱신한다. |
| FR-062 | “다음 일정으로 이동”은 같은 게임의 가장 가까운 미래 일정으로 이동한다. | `game_id`가 있고 `start_date >= KST 오늘`인 일정 중 가장 이른 것을 선택하고, 지출의 일정 연결 및 예정일을 해당 일정 종료일로 갱신한다. 대상이 없거나 일정 없는 항목이면 이동 액션을 제공하지 않는다. 갱신은 FR-033 검증을 통과해야 한다. |
| FR-063 | 오프라인에서는 유효 세션의 캐시 읽기만 허용한다. 만료 처리 모달은 닫을 수 있고 쓰기는 비활성화한다. | 온라인 복귀 시 서버에서 미해결 만료 행을 다시 조회하고, 인터랙티브 캘린더 전에 필수 처리를 재개한다. 인증 세션 만료 시 개인 캐시를 표시하지 않는다. |

### 4.8 아이콘 및 메모

## 5. 외부 인터페이스 및 환경

- **클라이언트**: Next.js App Router 정적 export, Windows용 Tauri v2 데스크톱 실행 파일, Android용 모바일 PWA. iOS PWA는 현재 범위에 포함하지 않는다.
- **서비스**: Supabase Auth(이메일/Google OAuth), PostgreSQL(RLS/RPC/트리거), 비공개 Storage.
- **시간**: 서버의 기한/결제 날짜 검증은 KST 기준을 사용한다. 저장 일시는 UTC `TIMESTAMPTZ`, 일정/목표일은 DATE로 관리한다.
- **금액**: 정수 KRW; 통화 변환 기능은 범위 밖이다.

## 6. 비기능 요구사항

| ID | 요구사항 | 수용 기준 |

구체적인 응답시간 목표는 설계 단계에서 지원 기기·네트워크·테스트 데이터 규모를 정한 뒤 확정하고 검증한다.

## 7. 핵심 상태 전이

| 현재 상태 | 명령 | 다음 상태 | 제약 |
|---|---|---|---|
| PLANNED | 결제 확정 | CONFIRMED | 결제 RPC 성공 시 원자 전환 |
| PLANNED | 예정 취소 | CANCELLED / PLANNED_CANCEL | 소유자 RPC만 |
| PLANNED | 구독 템플릿 비활성화 | CANCELLED / TEMPLATE_DEACTIVATION | 소유자가 템플릿을 비활성화하면 연결된 미결제 회차를 보존 취소 |
| CANCELLED / PLANNED_CANCEL | 복구 | PLANNED | 전용 복구 RPC만 |
| CANCELLED / TEMPLATE_DEACTIVATION | 복구 | PLANNED | 소유 템플릿이 먼저 활성화되어 있어야 하며, 복구 RPC는 템플릿 상태를 변경하지 않음 |
| CONFIRMED | 결제 환불 | CANCELLED / PAYMENT_REFUND | 환불 RPC 성공 시 원자 전환 |
| CANCELLED / PAYMENT_REFUND | 복구 시도 | 거부 | 환불 지출은 예정으로 되돌릴 수 없음 |

예정 취소 항목을 복구해도 목표일을 자동 변경하지 않는다. 목표일이 과거인 복구 항목은 온라인 복귀/캘린더 진입 시 다른 만료 예정 항목과 함께 다시 처리한다.

## 8. 주요 오류 응답

권한/소유권 불일치, 허용되지 않은 상태 전이, 금액 산식 불일치, 포인트 잔액 부족, 일정/게임 불일치, 템플릿 소유권 불일치, 미래 결제일, 적립 회수 후 음수 잔액 발생은 요청을 거부해야 한다. 결제·환불 거부는 어떤 관련 행이나 잔액도 부분 변경해서는 안 된다. 사용자에게는 원인을 식별할 수 있는 안내를 제공하되 내부 SQL/비밀정보는 노출하지 않는다.

## 9. 수용 및 검증 게이트

각 요구사항은 구현 시 해당 수용 기준을 검증 케이스로 추적해야 한다. 사용자는 SRS 요구사항을 승인했다. 테스트 프로젝트에서 rollback-only SQL 스모크 suite를 실행했고, `ON_ERROR_STOP=1` 상태에서 모든 검증 후 `PASS: all smoke-test fixtures and mutations rolled back`가 출력되어 테스트 변경이 롤백됐음을 확인했다. 이 스모크 검증은 핵심 DB/RPC/RLS 경로의 일부를 확인한 것이며 전체 SRS 수용 기준의 완전한 검증을 뜻하지 않는다. Phase 0.6 게이트를 통과해 설계 단계 진입을 승인한다. 전체 기능 및 비기능 수용 기준은 설계/테스트 계획에서 상세 케이스로 추적한다.
