## 1. 예정 지출 취소·삭제·재예정 (P0)

### 확정된 기획 규칙
* **물리적 삭제 금지**: 사용자가 캘린더에 등록해 둔 예정(`PLANNED`) 지출 항목(특히 정기 구독 생성분)에 대한 DB 레벨의 물리적 삭제(`DELETE`)는 전면 금지한다.
* **상태 전환(취소) 전용**: 예정 항목을 취소할 때는 **[예정 취소]** 액션으로 `PLANNED → CANCELLED` 처리한다. 사용자 지출의 물리 삭제는 허용하지 않는다.
* **명시적 복구**: 사용자 예정 취소 및 구독 템플릿 비활성화로 취소된 항목에 **[복구]**를 제공한다. 복구하면 기존 날짜를 보존하고 `PLANNED`로 전환한다. 기존 목표일이 과거라면 만료 처리 모달에 다시 포함한다. 확정 결제 환불은 예정 지출 복구 대상이 아니다.

### 엔지니어링 반영 요건
* expenses에 일반 사용자 DELETE 정책을 두지 않고 예정 취소 및 복구는 `cancel_planned_expense` / `restore_cancelled_expense` RPC로 제한한다. 환불은 `refund_expense_payment`로 별도 처리한다.

## 2. Google Play 포인트 적립 기준 (P1)

### 확정된 기획 규칙
* **시스템 즉시 계산**: 결제수단을 Google Play 또는 Galaxy Store로 선택한 경우에만 해당 스토어 적립률과 제품 내 예상 산식(`floor(실결제액 * 적립률 / 100)`)으로 예상 포인트를 계산하여, 결제 확정(`CONFIRMED`)과 동시에 해당 스토어 지갑에 **자동으로 즉시 가산**한다. WALLET 결제는 스토어 포인트를 사용해도 적립하지 않는다. 실제 스토어 정산액과 일치한다고 보장하지 않는다.
* **사용자 수동 보정 허용**: 스토어 정산 기준과 앱 예상 산식 간에 오차가 발생할 수 있음을 인정한다. 사용자가 설정 탭의 지갑 위젯에서 포인트 잔액을 직접 수정(보정)할 수 있는 기능을 제공한다.

### 엔지니어링 반영 요건
* 결제 RPC(`process_expense_payment`)의 기존 자동 계산 로직 유지.
* 기획 의도에 맞춰 사용자에게 잔액 보정 UI를 노출하고 `adjust_wallet_balance` RPC와 연동하여 수동 원장(`MANUAL_ADJUST`) 기록.

## 3. 지출의 참조 데이터 소유권과 관계 (P1)

### 확정된 기획 규칙
* **DB 레벨 참조 무결성**: 클라이언트(UI) 단에서 올바른 데이터만 넘겨준다고 신뢰하지 않고, 데이터베이스 내부에서 참조 무결성을 강제한다.
* 특정 게임의 일정(`schedule_id`)에 지출 예정액을 묶을 때, 해당 지출 레코드에 명시된 `game_id`와 일정 레코드 원본의 `game_id`가 일치하지 않으면 저장을 즉시 거부한다.
* 구독 템플릿 연결 시 템플릿 소유자와 지출 소유자가 일치해야 한다. 양쪽에 게임 ID가 있으면 이 값도 일치해야 한다.

### 엔지니어링 반영 요건
* `expenses` 테이블 생성 스키마 또는 가드 트리거에 검증 로직 추가: `IF NEW.schedule_id IS NOT NULL AND NEW.game_id IS DISTINCT FROM (SELECT game_id FROM game_schedules WHERE id = NEW.schedule_id) THEN RAISE EXCEPTION`.

## 4. 일정 종료 후 미결제 예정 지출 (P1)

### 확정된 기획 규칙
* **유저 확인 유도 (모달 강제 노출)**: `PLANNED` 상태로 목표일이 지난 항목은 시스템이 자동으로 취소하지 않는다.
* 온라인 캘린더 진입 시 기한이 지난 항목을 감지해 전용 모달을 표시한다. 온라인에서는 미처리 항목이 남은 동안 처리를 완료해야 한다.
* 사용자는 각 항목에 대해 **[결제 확정]**, **[예정 취소]**, 가능한 경우 **[다음 일정으로 이동]** 중 하나를 선택한다. 오프라인에서는 캐시 조회 및 모달 닫기를 허용하고 온라인 복귀 후 처리를 재개한다.

### 엔지니어링 반영 요건
* KST 기준 `target_date < 오늘`인 모든 `status = 'PLANNED'` 레코드(구독 포함)를 페치한다. 온라인에서는 필수 처리를 요구하고 오프라인에서는 캐시 조회 및 모달 닫기를 허용하며, 온라인 복귀 후 다시 처리한다.
* 다음 일정 이동은 같은 게임의 `start_date >= 오늘`인 가장 가까운 일정으로 하며, 예정일은 해당 일정 종료일로 정한다. 후보 일정이 없으면 이동 액션을 제공하지 않는다.
* 미처리 시 해당 예정액은 기한 만료 상태로 계속 당월 예상 소비액 계산식에 합산되도록 유지.

## 5. 신규 사용자 재정 초기화 (P1)

### 확정된 기획 규칙
* **백그라운드 무음 초기화**: 신규 가입자가 앱을 처음 켰을 때, 자산/예산을 입력하라는 온보딩 팝업으로 피로도를 주지 않는다. (온보딩 생략)
* 가입과 동시에 시스템이 백그라운드에서 총 자산 0원, 월 기본 예산 0원, 스토어 지갑(구글 플레이/갤럭시 스토어) 0원의 기초 데이터를 자동으로 생성해 둔다. 사용자는 추후 필요할 때 우측 사이드바(히어로 영역)를 통해 금액을 자유롭게 수정한다.

### 엔지니어링 반영 요건
* `SCHEMA.sql`에 정의된 `handle_new_user_setup()` 및 `auth.users` INSERT 트리거로 재무 기본값과 Google/Galaxy 지갑을 멱등 생성한다. 신규 예산 행은 생성하지 않고 `default_budget=0`을 폴백으로 사용한다.

## 추가 결정 및 정합성 보완 (2026-10-02)

사용자 선택 **2번**을 반영한다. 오프라인에서는 인증 세션이 유효한 동안 캐시 읽기를 허용하고, 만료 처리 모달을 닫을 수 있다. 오프라인 쓰기는 비활성화한다. 온라인 복귀 시 미해결 만료 항목을 다시 조회해 처리하도록 강제한다.

- 예정 취소와 확정 결제 환불을 구분한다. 예정 취소만 `PLANNED_CANCEL` 원인으로 복구할 수 있고, 환불은 `PAYMENT_REFUND`로 기록하며 복구할 수 없다. 지출 물리 삭제는 금지하고 UI 액션은 **[예정 취소]**로 부른다.
- `floor(final_amount * earn_rate / 100)`은 제품 내 예상 적립 산식이다. Google Play의 공식 정산액을 그대로 보장한다고 표현하지 않는다. 잔액 수동 보정은 `MANUAL_ADJUST` 원장 행이며, 개별 환불은 결제와 연결된 사용/예상 적립을 되돌리고 별도 수동 보정 행은 변경하지 않는다.
- 일정 연결 시 게임 ID 일치를 강제하며, 구독 템플릿 연결 시 템플릿 소유자와 지출 소유자가 같아야 한다. 템플릿과 지출 모두 게임 ID가 있으면 그 값도 일치해야 한다.
- 만료 집합은 KST 오늘 기준 `target_date < today AND status='PLANNED'`인 전체 지출이다. 같은 게임의 `start_date >= today`인 가장 가까운 미래 일정으로 이동하며, 그런 일정이 없으면 이동 액션을 제공하지 않는다. 이동 후 예정일은 대상 일정 종료일이다.
- 사용자가 후속으로 선택한 정책: 과거 목표일의 예정 취소 항목을 복구하면 날짜는 변경하지 않고, 해당 항목을 만료 처리 모달에 다시 표시한다.
- 사용자가 후속으로 확정한 환불 정책: 환불은 해당 결제 행에 기록된 포인트 사용 및 예상 적립만 되돌린다. 독립적인 `MANUAL_ADJUST` 원장과 잔액 보정은 그대로 유지한다.
- 사용자가 기존 총 자산 차감 토글 정책을 유지하기로 확정했다. `deduct_from_asset=true`일 때 실결제액을 자산에서 차감하고 환불 시 복원한다. 오늘 결제는 기본 켬, 과거 내역은 기본 끔이며 사용자가 변경할 수 있다.
- 사용자가 본인 계정 삭제 시 개인 데이터도 삭제하기로 결정했다. 계정 유지 중 개별 지출 물리 삭제 금지와 구분하며, 계정 삭제 완료 시 소유 개인 레코드와 비공개 아이콘을 제거하고 공용 카탈로그/일정은 보존한다.
- 사용자는 Google Play/Galaxy Store를 결제수단으로 선택했을 때만 해당 스토어 적립률로 예상 포인트를 적립하기로 확정했다. WALLET 결제에 스토어 포인트를 사용하더라도 적립은 없다.
- 사용자는 구독 템플릿 비활성화 시 이미 생성된 미결제 회차도 취소하기로 결정했다. 재활성화는 향후 생성만 재개하고 기존 취소 회차는 자동 복구하지 않는다. `TEMPLATE_DEACTIVATION` 원인을 기록하며 수동 복구는 허용한다.
- 사용자는 구독 템플릿의 물리 삭제를 금지하고 조회·추가·수정 및 비활성화만 허용하기로 결정했다.
- `TEMPLATE_DEACTIVATION` 회차는 소유 템플릿을 먼저 재활성화한 뒤 명시적으로 복구할 수 있다. 일반 예정 취소 복구와 환불 복구 규칙은 별도로 유지한다.
- 사용자가 월별 예산 0원은 미설정으로 보고 기본 예산을 적용하기로 결정했다. 월별 예산 행이 없거나 0원일 때 `default_budget`을 사용하며, 최종 적용 예산도 0원이면 80%/100% 비율 경고와 초과 확인을 생략한다.
- 사용자는 100% 초과 확인을 새 등록뿐 아니라 예상 소비액을 증가시키는 수정·복구·결제 변경에도 적용하기로 결정했다. 저장/확정 전에 확인하며 적용 예산 0원은 제외한다.
- 신규 가입 트리거는 기존 DDL에 실제로 없었으므로 `SCHEMA.sql`에 추가했다. 기본값은 자산 0, 기본 예산 0, Google BRONZE/0.10%/잔액 0, Galaxy/0.10%/잔액 0이다. 당월 월별 예산 행은 필수 생성하지 않고 기본 예산을 폴백으로 사용한다.
- 상세 요구사항 기준은 [SRS.md](SRS.md)이며 기능 화면 요약은 [SPEC.md](SPEC.md), 데이터베이스 초안은 [SCHEMA.sql](SCHEMA.sql)을 따른다. SQL은 배포 전 실행 검증이 필요하다.
