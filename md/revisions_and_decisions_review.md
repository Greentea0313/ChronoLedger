## 요약

제품 요구사항 일부는 갱신됐지만, 내장된 DDL·RPC·RLS에는 앞서 합의한 수정이 반영되지 않았거나 서로 충돌하는 부분이 남아 있다. 특히 결제 RPC와 클라이언트 직접 쓰기 경로는 자산·포인트 무결성에 영향을 줄 수 있어 우선 수정해야 한다. 이 문서는 정적 검토 결과이며 SQL을 실행하거나 데이터베이스에서 재현 검증하지 않았다.

## 적용 전 필수 수정

### 1. 결제 RPC가 지출 행과 상태를 검증하지 않음 — 심각도: 매우 높음

`process_expense_payment`는 포인트·자산을 먼저 변경한 뒤 `expenses` 행을 갱신한다. 지출 ID가 본인 소유인지, 존재하는지, `PLANNED` 상태인지 먼저 `SELECT ... FOR UPDATE`로 확인하지 않는다(명세 SQL 308–388행). UPDATE가 행을 찾지 못해도 앞선 지갑·자산 변경은 함수 실행에서 정상 완료될 수 있다. 이미 확정된 건을 다시 호출하는 것도 막지 않는다.

**수정:** 지출 행을 소유자 기준으로 잠그고 존재 및 `PLANNED` 여부를 검증한 뒤 모든 검증과 변동을 진행한다. 마지막 상태 전환까지 한 트랜잭션으로 처리하고, 실패 시 전체 롤백되도록 한다.

### 2. 결제 금액·포인트 적립값을 클라이언트가 결정함 — 심각도: 매우 높음

RPC가 `p_earned_points`, `p_final_amount`를 인자로 받지만 서버에서 재계산하지 않는다(308–318행, 354–386행). 이로 인해 임의 적립액 또는 회계 값 불일치를 허용할 수 있다. NULL, 음수, 결제 수단, 할인 범위 및 미래 결제일에 대한 명시 검증도 없다.

**수정:** 서버에서 `final_amount = original_price - discount_amount - point_discount_amount`를 계산하고 음수 여부를 검증한다. 적립률은 잠근 지갑 설정에서 읽어 `FLOOR(final_amount * earn_rate / 100)`으로 계산한다. 결제 수단과 필수 입력을 허용 목록으로 검증한다. 사용자가 날짜를 입력하는 기능을 유지한다면 결제일을 RPC 매개변수로 받아 KST 오늘 이후 날짜를 거부한다.

### 3. 지출 직접 쓰기 차단 가드가 없고 기본 상태가 잘못됨 — 심각도: 매우 높음

`expenses.status` 기본값이 아직 `CONFIRMED`다(247–278행). 문서에서 결정한 `PLANNED` 기본값과 다르며, 내장 SQL에는 클라이언트의 확정·금액·포인트 필드 직접 변경을 차단하는 가드 트리거도 없다. `Manage own expenses FOR ALL` 정책은 본인 지출 행의 직접 쓰기를 허용한다(559행).

**수정:** 기본값을 `PLANNED`로 바꾸고 클라이언트 직접 삽입은 예정 건만 허용한다. 확정·환불 및 포인트 필드 변경은 RPC만 허용하고, 확정 내역의 회계 필드 변경을 트리거 또는 더 제한적인 권한으로 막는다.

### 4. 자산과 RPC 권한 보호가 미흡함 — 심각도: 매우 높음

`user_finances`에 `FOR ALL` 정책을 주어 사용자가 `total_asset`을 직접 변경할 수 있다(554행). 또한 SQL에 RPC의 `REVOKE ... FROM PUBLIC, anon` 및 `GRANT ... TO authenticated` 선언이 없다. `SECURITY DEFINER` 함수는 권한을 명시적으로 제한해야 한다.

**수정:** 자산 잔액 직접 UPDATE를 막고 자산 설정에 필요한 별도 안전 경로와 결제·환불 RPC를 구분한다. 각 SECURITY DEFINER 함수의 기본 EXECUTE 권한을 회수하고 인증 사용자에게 필요한 함수만 부여한다. 함수마다 사용자 인증, 입력 검증, 고정 `search_path`를 확인한다.

### 5. 포인트 스토어 식별을 결제수단으로 대신함 — 심각도: 높음

`expenses`에 `point_platform` 컬럼이 없다(247–278행). 환불 함수는 `payment_method`가 `GOOGLE_PLAY` 또는 `GALAXY_STORE`인지로 포인트 지갑을 찾는다(411–435행). 신용카드와 포인트를 함께 쓰는 복합 결제에서 실제 포인트 출처를 보존하지 못하므로 요구사항과 맞지 않는다. 원장 환불 두 항목의 `balance_after`도 같은 최종 잔액으로 기록되어 중간 잔액 흐름과 맞지 않는다.

**수정:** 지출에 `point_platform`을 별도로 저장하고 결제·환불 모두 이를 기준으로 지갑을 찾는다. 사용 포인트 반환과 적립 포인트 회수를 순차 처리하고 각 원장 행의 `balance_after`를 해당 시점 잔액으로 기록한다.

### 6. 일정 요청 승인·반려 경로 및 요청 메모가 누락됨 — 심각도: 높음

본문은 사용자의 일정 추가·수정 요청과 관리자 승인을 약속하지만(2.4절), SQL에는 결제·환불·지갑 설정·보정 RPC만 있다(304–497행). `approve_schedule_request`, `reject_schedule_request`가 없고 `schedule_requests.memo`도 없어 요청 설명을 승인된 일정에 반영할 수 없다(196–209행).

**수정:** 요청 메모 컬럼을 추가하고 승인 RPC가 신규·수정 일정에 메모를 전달하도록 한다. 승인/반려 RPC는 관리자 역할, 대기 상태, 대상 일정 및 게임 일치를 확인하고 일정 반영과 요청 상태 전환을 한 트랜잭션으로 처리한다.

### 7. 일정 변경 동기화가 부분적이고 범위가 넓음 — 심각도: 높음

트리거는 `end_date` 변경만 감지하며 `target_date`, `end_date`만 갱신한다(499–516행). 시작일과 `start_date` 동기화가 빠져 있고, `PICKUP` 일정도 모두 동기화 대상이 된다. 본문은 버전 변경 시 예정 지출 날짜를 동기화한다고 설명한다.

**수정:** 변경 전후 날짜의 `IS DISTINCT FROM` 비교를 사용해 NULL 안전성을 확보한다. 명세가 정의한 `VERSION` 일정에 한해 연결된 `PLANNED` 항목의 시작일·종료일·예정일을 갱신하고 `CONFIRMED`는 보존한다. 픽업에도 같은 동작이 필요한지 별도 결정한다.

### 8. 수동 지갑 보정의 무행·음수 버그가 남아 있음 — 심각도: 높음

`adjust_wallet_balance`는 지갑 행이 없는 경우 `SELECT ... INTO`가 행을 반환하지 않아 `v_current`가 NULL일 수 있다(483–495행). `COALESCE`는 반환 행 내부의 NULL은 처리하지만 무행 결과를 0으로 바꾸지는 않는다. 목표 잔액 음수 및 플랫폼 오류도 차단하지 않는다.

**수정:** 먼저 지갑 행을 `INSERT ... ON CONFLICT DO NOTHING`으로 확보한 다음 `FOR UPDATE`로 잠근다. 플랫폼 허용 목록, NULL 여부, `p_target_balance >= 0`을 검증하고 현재 잔액과 보정 원장을 같은 트랜잭션에서 갱신한다.

## 추가로 반영할 수정

- **지갑 설정 검증:** `update_store_wallet_settings`가 플랫폼·등급·적립률 조합을 검증하지 않는다(449–466행). Google Play는 확정된 공식 등급별 비율을 강제하고, Galaxy Store는 사용자가 적립률을 조정하며 등급은 NULL로 제한한다. 현재 스키마는 비율 상한 및 등급 CHECK도 없다(234–244행).
- **요청 INSERT RLS:** 사용자 본인 여부만 확인하고 `request_status = 'PENDING'`, `admin_memo IS NULL`을 강제하지 않는다(546–551행). 사용자가 승인 상태나 관리자 메모를 직접 입력하지 못하도록 정책을 제한한다.
- **구독 멱등성:** 유일 인덱스는 취소 회차에도 남아 자동 재생성을 막으므로 의도와 부합한다(280–283행). `is_active` 템플릿만 생성하도록 체크리스트에 명시하고, 재예정은 자동 재생성이 아닌 명시적 RPC/사용자 액션으로 설계한다.
- **월 집계 규칙:** `CONFIRMED = target_date 월`, `PLANNED = COALESCE(end_date, target_date) 월`, `CANCELLED 제외`가 SQL·UI·예산 경고의 공통 규칙으로 문서화되어 있지 않다.
- **소급 입력 기본값:** 현재 UI 설명은 과거 입력 시 자산 차감 체크 해제라고 하지만 SQL RPC에는 결제일 입력이 없어 작동 경로가 완성되지 않았다. 과거 결제 기본 false, 사용자 안내 및 서버 날짜 검증을 함께 정리한다.
- **픽업 전반·후반:** UI는 전반·후반을 구분하지만 `game_schedules`에는 `phase`나 상위 버전 참조가 없다. 명시 필드를 추가할지, 탭을 기간 필터로 바꿀지 결정해야 한다.
- **스키마 제약과 인덱스:** `billing_cycle` 형식 CHECK, `subscription_templates.payment_method` 허용값, 포인트 할인/플랫폼 조합 제약, `personal_memos` 공백 내용 검증이 빠져 있다. 앞서 제안한 `expenses(schedule_id)`, `store_point_transactions(user_id, platform)`, `schedule_requests(request_status)` 인덱스도 추가 검토한다. `personal_memos`에는 하루 다건을 허용하고 `UNIQUE(user_id, memo_date)`를 두지 않는다.
- **게임 PENDING 상태:** 현재 `games.status`는 `PENDING`을 허용하지만 게임 등록 요청 테이블/승인 흐름은 없다(160–168행). 게임 요청 흐름을 추가하거나 상태를 제거해야 한다.
- **Storage 정책:** 체크리스트에는 `user-icons/{user_id}/{game_id}.webp` 업로드와 캐시 쿼리 규칙만 있고 버킷 공개 범위, 소유자 경로 RLS, 형식·크기 정책이 없다. 배포 정책으로 구체화한다.
- **트리거 수 설명:** 문서에는 네 RPC와 동기화 트리거만 명시되어 있지만 `updated_at` 유틸, 신규 사용자 초기 설정, 지출 가드의 실제 구현 여부와 개수가 정리되지 않았다. DDL과 설명을 일치시킨다.
- **검증 재현성:** 체크리스트는 Vitest 및 수동 RPC 검증을 언급하지만 이전에 제안한 `TESTS.sql`과 테스트 역할/JWT, 초기 데이터, 실행 순서, 기대값을 제공하지 않는다. PASS 숫자는 실제로 재현하기 전에는 검증 완료 근거로 쓰지 않는다.
- **정적 export/PWA 정책:** 서버 기능 제약과 오프라인 읽기 전용 정책이 구체적으로 정의되지 않았다. 특히 현재 체크리스트의 오프라인 동작은 쓰기 버튼 잠금만 다루므로 읽기 가능한 캐시 데이터와 인증 만료 동작도 정해야 한다.

## 권장 수정 순서

1. 결제 RPC 상태·소유권 잠금, 서버 금액 계산, 포인트 플랫폼 분리를 먼저 바로잡는다.
2. 지출 가드, 자산 직접 쓰기 제한, SECURITY DEFINER 권한 회수/부여 및 요청 RLS를 완성한다.
3. 일정 승인·반려 RPC와 요청 메모, 일정 동기화 범위를 보완한다.
4. 지갑 설정/보정 검증, 구독 생성·재예정, 월 집계 및 소급 입력 규칙을 맞춘다.
5. 남은 제품 결정을 확정하고 스키마·UI·Storage·체크리스트에 동일하게 반영한다.
6. 재현 가능한 DB/RPC/RLS 회귀 테스트를 작성하고 실행 결과를 기록한다.

## 확인하지 않은 사항

- SQL을 PostgreSQL/Supabase에서 실행하지 않았다.
- 보안 취약점의 실제 악용 여부나 테스트 결과를 확인하지 않았다. 심각도 평가는 내장 SQL의 정적 읽기에 따른 위험도다.
- 본 문서는 대상 명세를 수정하지 않고 별도 검토 기록으로 작성했다.
