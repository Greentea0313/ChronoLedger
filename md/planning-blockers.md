## 1. 예정 지출 취소·삭제·재예정 — P0

### 현재 명세와 충돌

`md/SCHEMA.sql`의 예정 지출 UPDATE 정책은 기존 상태와 변경 후 상태를 모두 `PLANNED`로 제한한다. 따라서 사용자는 예정 지출을 `CANCELLED`로 바꿀 수 없다. 반면 DELETE 정책은 `template_id`가 있는 구독 생성 지출도 구분 없이 삭제할 수 있다. 이 경우 해당 회차의 취소 이력이 사라지고, `UNIQUE(template_id, billing_cycle)`이 더는 재생성을 막지 않아 다음 캘린더 로드 때 다시 생성될 수 있다.

요구사항은 구독 지출을 물리 삭제하지 않고 `CANCELLED`로 보존해 자동 재생성을 방지한다고 정한다. 현재 접근 정책은 이 핵심 규칙을 지키지 못한다.

### 사용자에게 보이는 영향

- 구독 항목을 취소하려 해도 권한 오류가 발생할 수 있다.
- 삭제 동작이 허용되면 취소한 구독료가 다음 화면 로드에서 되살아날 수 있다.
- 취소한 회차를 사용자가 나중에 다시 예정으로 만들 방법도 정의되어 있지 않다.

### 결정 및 완료 기준

1. 일반 예정 지출과 템플릿에서 생성된 구독 지출의 취소/삭제 정책을 각각 결정한다.
2. `PLANNED → CANCELLED` 전환은 소유자에게 허용하되, 구독 지출은 직접 DELETE를 금지한다.
3. 취소 회차 재예정은 자동 생성으로 처리하지 않는다. 명시적 사용자 액션이 같은 레코드를 되살릴지 새 회차를 만들지 결정한다.
4. 결정한 흐름을 RLS, RPC, 유일성 규칙, UI 버튼/확인 메시지에 동일하게 반영한다.
5. 검증 시 일반 예정 지출 취소, 구독 예정 지출 취소, 삭제 시도, 같은 달력 재접속, 명시적 재예정을 각각 확인한다.

## 2. Google Play 포인트 적립 기준 — P1

### 현재 명세와 충돌/불명확성

명세는 한국 등급별 비율을 공식 기준이라고 설명하면서 적립액을 `ROUND(final_amount * earn_rate / 100)`으로 계산한다. `final_amount`는 정가에서 일반 할인과 포인트 할인액을 모두 뺀 값이다. Google 도움말은 등급에 해당하는 기본 적립률을 상품 가격에 적용하고 세금을 제외한다고 설명하며, 계산값은 가장 가까운 정수로 반올림한다고 안내한다. 따라서 세금 포함 가격인지, 일반 쿠폰 할인 후 금액인지, Play Points 사용액을 뺀 금액인지가 정해지지 않으면 “공식 계산”을 재현한다고 보장할 수 없다.

공식 등급별 비율은 [Google Play 한국 등급·혜택 안내](https://support.google.com/googleplay/answer/9080348?co=GENIE.CountryCode%3DKR&hl=ko)에서 확인할 수 있고, 산정·반올림 설명은 [Google Play 포인트 적립 안내](https://support.google.com/googleplay/answer/9077192?co=GENIE.CountryCode%3DKR&hl=ko-KR)에 있다.

### 사용자에게 보이는 영향

지출 화면의 예상 적립 포인트와 실제 Google Play 지급 포인트가 달라질 수 있다. 예산에는 직접 영향이 없어도 포인트 지갑 잔액과 환불 가능 여부가 틀어질 수 있다.

### 결정 및 완료 기준

1. 포인트 적립 대상 금액을 상품 표시 가격, 세금 제외 상품 가격, 할인 후 금액, 포인트 차감 전/후 금액 중에서 확정한다.
2. 세금 정보를 입력받지 않는다면 실제 지급액을 보장하지 않는 “예상 적립” 기능으로 명시한다.
3. 경계값과 반올림 규칙을 구체적으로 정의한다. 예를 들어 0.5 포인트 및 지역 최소 적립 기준을 어떻게 처리할지 적는다.
4. 동일 산식을 SRS, 결제 UI, SQL RPC, 예산/지갑 표시 및 검증 케이스에 적용한다.

## 3. 지출의 참조 데이터 소유권과 관계 — P1

### 현재 명세와 충돌/누락

지출 INSERT 정책은 지출의 `user_id`, 상태, 포인트 필드만 제한한다. 외래키는 해당 ID가 존재하는지만 보장하며, `template_id`가 지출 소유자의 구독 템플릿인지, `schedule_id`와 `game_id`가 서로 같은 게임을 가리키는지까지 보장하지 않는다. 요청·클라이언트가 임의 UUID를 전달할 수 있는 구조라면 다른 사용자의 템플릿 회차 키를 선점할 수 있다.

### 사용자에게 보이는 영향

사용자 데이터가 다른 사용자의 템플릿·일정에 연결되거나, 원래 소유자의 구독 지연 생성이 유일 인덱스 충돌로 실패할 수 있다. 게임 선택 UI만 검증하고 DB에서 확인하지 않으면 API를 직접 호출해 규칙을 우회할 수 있다.

### 결정 및 완료 기준

1. `template_id`가 지정되면 해당 템플릿의 소유자가 현재 사용자이고, `billing_cycle`이 일치하는지 확인한다.
2. `schedule_id`가 지정되면 일정의 게임과 지출의 게임이 같은지 확인한다.
3. 제품 규칙상 “내 게임”에 등록한 일정만 연결해야 한다면 `user_games` 존재 여부도 검증한다.
4. 같은 조건을 지출 생성과 예정 지출 수정 양쪽에서 강제한다. UI 검증은 편의 기능이고 DB 검증은 보안·정합성 경계로 둔다.
5. 다른 사용자 템플릿, 다른 게임 일정, 존재하지 않는 참조 ID를 사용한 호출이 거부되는지 확인한다.

## 4. 일정 종료 후 미결제 예정 지출 — P1

### 현재 명세와 충돌/누락

일정 종료일을 기준으로 예정액을 월 예산에 귀속하고, 체크리스트에는 만료 처리도 언급한다. 그러나 스키마의 지출 상태는 `PLANNED`, `CONFIRMED`, `CANCELLED`뿐이다. 일정 종료 뒤 미결제 항목을 계속 예정으로 남길지, 취소할지, 사용자가 처리할 때까지 경고할지 정의되어 있지 않다.

### 사용자에게 보이는 영향

마감이 지난 예정액이 예산에 계속 잡힐 수 있고, 자동 취소한다면 사용자가 구매 의사를 유지하는 항목이 사라질 수 있다. 전월/익월 예산 귀속도 종료 후 동작에 따라 달라진다.

### 결정 및 완료 기준

1. 일정 종료 직후 자동 상태 변경 여부와 알림/모달 시점을 결정한다.
2. 자동 취소, 예정 유지, 사용자 확인 중 어떤 방식인지 정하고 결제·취소·일정 이동 버튼을 명시한다.
3. 만료 항목이 어떤 월의 예상 소비액에 계속 포함되는지 정한다.
4. 오프라인 상태나 사용자가 앱을 오래 열지 않은 경우의 처리 시점도 정한다.
5. 종료일 전·당일·후, 두 달 일정, 과거 결제 및 이미 취소된 건을 검증한다.

## 5. 신규 사용자 재정 초기화 — P1

### 현재 명세와 충돌/누락

결제 RPC는 자산 차감이 선택되면 `user_finances` 행을 갱신하고 행이 없으면 오류를 반환한다. 자산·기본 예산을 만드는 설정 RPC는 있지만, 가입 직후 또는 첫 로그인 때 언제 호출되는지, 초기 설정 전 캘린더/예정 지출/결제를 허용할지 연결되어 있지 않다.

### 사용자에게 보이는 영향

초기화가 누락된 사용자는 결제 확정에서 오류를 만날 수 있다. 첫 실행에서 기본 예산이 0원으로 표시되는지, 설정을 건너뛸 수 있는지도 사용자 경험에 영향을 준다.

### 결정 및 완료 기준

1. `user_finances` 생성 시점을 가입 트리거, 첫 로그인 온보딩, 명시적 설정 RPC 중에서 선택한다.
2. 초기 자산과 기본 예산의 기본값 및 설정 건너뛰기 허용 여부를 정한다.
3. 초기화 RPC의 재호출이 사용자 잔액을 의도치 않게 덮어쓰지 않도록 신규 설정과 잔액 정정을 분리할지 결정한다.
4. 설정 전 결제 동작과 초기화 실패 시 안내/재시도 동작을 요구사항으로 적는다.

## SRS 및 설계 게이트

각 항목은 SRS에서 고유 요구사항 ID, 우선순위, 사전 조건, 정상/오류 흐름, 수용 기준으로 표현한다. 결정이 필요한 정책을 임시 가정으로 채우지 않는다. 다섯 항목을 확정하고 마스터 명세·`SPEC.md`·`SCHEMA.sql`을 동기화한 다음 SRS를 검토한다. 리뷰 및 추적성 확인이 완료되어야 설계 기준선을 승인한다.

현재 문서는 차단 항목을 설명한 검토 자료다. SQL 실행이나 자동 테스트 결과를 의미하지 않는다.
