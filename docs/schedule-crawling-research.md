# 공식 일정 자동 수집(크롤링) 가능성 조사 (R86)

- **작성**: Claude Opus (Run `r86-schedule-crawling-research` Step 1), 2026-11-11
- **성격**: 문서 전용 조사임. 코드·DB 변경 없음. 법률 자문이 아니며, 약관 해석은 원문 재확인이 필요함.
- **확인 방법**: 공개 웹 검색, 공개 `robots.txt`·API 문서 조회, Steam 공개 API 표본 호출(2026-11-11). 사용자 정보는 외부 요청에 넣지 않음.
- **한계**: 조사 도구가 JavaScript로 그려지는 페이지와 일부 도메인(`game.naver.com`, `policy.naver.com`, `x.com` 약관 페이지, HoYoverse 약관 페이지)을 열지 못해 해당 원문은 2차 자료로만 확인함. 이런 항목은 `확인 필요`로 표시함.

## 1. 결론 요약

- **완전 자동 등록은 권장하지 않음.** 공식 공지에 픽업·이벤트 기간이 일정한 형식으로 나오지 않고, 한국 공식 커뮤니티(네이버 게임 라운지)와 X는 약관상 자동 수집이 금지되거나 금지로 해석됨.
- **권장안: "후보 감지 + 관리자 승인" 반자동 방식 + "버전 주기 추정"의 조합.**
  1. **Steam 공식 공지 감지**: Steam에 있는 6개 게임은 공개 Steam 뉴스 API(`ISteamNews/GetNewsForApp`, 키 불필요)로 공식 공지(`feedname = steam_community_announcements`)만 읽어, 버전·업데이트·점검 공지가 새로 올라오면 **관리자 검토 대기 항목**을 만듦. 기간은 관리자가 확정함.
  2. **버전 주기 추정**: 버전 주기가 일정한 게임(예: HoYoverse 계열)은 수집 없이 마지막 버전 일정 + 주기로 **다음 버전 예상 일정**을 만들어 관리자에게 제안함(외부 요청 없음).
  3. 나머지 출처(네이버 라운지·X·비공개/비문서화 API)는 **수집 대상에서 제외**함.
- **1차 구현 범위 제안**: Steam 공지 감지(6개 게임) + 버전 주기 추정(관리자가 주기를 설정한 게임). 실행 환경은 Supabase Edge Function + `pg_cron`을 우선 후보로 둠.

## 4. Steam 공지 표본에서 확인한 형식 (2026-11-11)

- **피드 혼재**: 명조·엔드필드 응답에 외부 매체 피드(`PlayGround.ru - официальная группа`)가 섞여 있음 → `feedname = steam_community_announcements`만 사용해야 함.
- **날짜 표기가 제각각**: 제목에 `2026.11.12 (KST)`(림버스), 본문에 `Oct. 15, 2026 at 06:00 – … (UTC+8)`(엔드필드), `10/29 (Thu) 14:10 (UTC)`(에픽세븐) 등 게임마다 형식과 시간대가 다름.
- **픽업 기간은 드묾**: 표본 공지에는 픽업(소환) 시작·종료 기간이 거의 없음. 버전 업데이트·점검 공지는 감지 신호로 쓸 수 있음.
- **결론**: 공지에서 기간을 자동으로 확정하지 말고, "새 버전/업데이트 공지 감지 → 관리자 검토 대기"로 쓰는 것이 안전함. 날짜가 확실히 파싱되면 초안 값으로만 채움.

## 6. 데이터 흐름 제안 (반자동)

- **원칙**: 수집 결과는 공용 일정(`game_schedules`)에 바로 쓰지 않고 관리자 승인을 거침.
- **현재 구조의 제약**: `schedule_requests`는 `user_id`(가입 사용자)와 `start_date`·`end_date`가 필수임. 수집기는 사용자가 아니고, 감지한 공지에는 종료일이 없는 경우가 많음.
- **선택지 (다음 Run에서 결정 필요)**:
  - **A. 별도 테이블 `schedule_candidates`** (권장): 게임·출처(`steam:appid`)·외부 ID(Steam `gid`)·제목·원문 링크·감지 시각·추정 시작/종료(선택)·상태(`NEW/DISMISSED/CONVERTED`)를 저장함. 외부 ID에 UNIQUE를 걸어 중복을 막음. 관리자가 후보를 열어 기존 일정 폼으로 일정을 만들면 `CONVERTED`로 바꿈. 관리자만 읽고 쓰는 RLS.
  - **B. `schedule_requests` 재사용**: 전용 "수집 봇" 계정을 만들고 출처 컬럼을 추가함. 기존 승인 화면을 그대로 쓰지만, 날짜 필수 조건 때문에 추정 날짜를 강제로 넣어야 하고 사용자 요청과 섞임.
- **버전 주기 추정**: 게임별 설정(예: `version_cycle_days`, 관리자 입력)과 마지막 VERSION 일정으로 다음 버전 예상 시작일을 계산해 같은 후보 목록에 `source = estimate`로 올림. 외부 요청이 없어 약관 문제가 없음.
- **수정 공지 반영**: 같은 외부 ID의 공지가 수정되면 후보를 `NEW`로 되돌려 다시 검토하게 함.

## 7. 유지보수 위험

- 공지 형식·시간대 표기가 게임마다 다르고 바뀔 수 있어, 날짜 자동 파싱은 실패를 전제로 둬야 함(실패해도 후보는 만들고 날짜만 비움).
- Steam에 없는 게임(HoYoverse 3종, 니케, 명일방주 등)은 공식 공개 API가 확인되지 않아 수집 대상을 늘리기 어려움.
- Steam 약관·API는 예고 없이 바뀔 수 있음. 호출 실패 시 후보 생성만 멈추고 앱 기능에는 영향이 없게 설계함.
