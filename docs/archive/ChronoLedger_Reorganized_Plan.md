# ChronoLedger 기획 재정리 및 설계 가이드

이 문서는 에이전트가 임의로 UI나 기능을 추측하여 구현하는 것을 방지하고, 각 화면의 역할과 데이터 간의 유기적 연결을 엄격하게 통제하기 위한 기획 재정리 문서입니다. 승인된 SRS 및 설계 문서를 바탕으로 작성되었습니다.

---

## 1. 페이지 구성 및 명확한 UI 배치

ChronoLedger는 단일 Next.js 코드베이스(App Router)로 구성되며, 데스크톱(Windows Tauri)과 모바일(Android PWA) 레이아웃을 반응형으로 지원합니다.

### 1) `/auth` (인증 화면)
*   **기능**: 이메일/비밀번호 로그인, 회원가입, Google 로그인 (OAuth PKCE 방식).
*   **UI 배치**: 
    *   앱 기본 다크 테마 적용.
    *   입력 폼(이메일, 비밀번호)에는 명시적 레이블 제공, 키보드 탭 순서(이메일→비밀번호→로그인→가입→Google) 준수.
    *   320/390px 모바일 화면에서도 가로 넘침이 없는 세로형 스택 레이아웃 적용. 버튼 터치 영역 최소 44~48px 보장.

### 2) `/dashboard` (캘린더 기반 메인 화면)
*   **기능**: 이번 달 예산 소진 현황 요약, 공용 게임 일정(VERSION/PICKUP) 확인, 개인 메모 표시. (오프라인 캐시 읽기 허용)
*   **UI 배치 (Desktop)**: 좌측 메인 영역에 전체 캘린더 배치, 우측 사이드바에 상세 내역(선택일 지출/메모/일정)과 예산(월 예산 대비 소진율) 패널 배치.
*   **UI 배치 (Mobile)**: 상단에 캘린더 표시, 달력 날짜 터치 시 하단에서 올라오는 **바텀 시트(Bottom Sheet)**에 상세 내역 표시.
*   **엄격한 제한**: 월간 캘린더 타일 안에는 **금액이나 개별 지출 내역을 절대 텍스트로 표기하지 않습니다**. 오직 게임 아이콘, 일정 배너, 단일 메모 도트(여러 개의 메모가 있어도 도트 하나)만 표시하여 시각적 복잡도를 최소화합니다. 미니 차트 등은 배제합니다.

### 3) `/expenses` (가계부 목록 화면)
*   **기능**: 사용자의 모든 확정(CONFIRMED), 예정(PLANNED), 취소(CANCELLED) 지출 내역을 조회하고 상태를 변경(결제 확정, 예정 취소, 환불)하는 메인 작업 공간.
*   **UI 배치 (Desktop)**: 한눈에 비교할 수 있는 **테이블(표)** 형태 우선 배치.
*   **UI 배치 (Mobile)**: 날짜별로 그룹화된 **카드** 형태 (좁은 폭에서의 가독성을 위해).

### 4) `/statistics` (통계 화면)
*   **기능**: 소비 추이, 게임/결제 플랫폼별 비중 분석.
*   **UI 배치**: 월별 소비 추이는 **세로 막대그래프**, 카테고리(게임별, 플랫폼별) 비중은 **가로 막대그래프**를 사용하여 시각적으로 일관되게 표현.

### 5) `/settings` & `/admin` (설정 및 관리)
*   **기능**: 내 자산/예산 설정, 지갑(구독 스토어 적립률, 잔액 보정) 설정, 내 게임 목록 구독 관리, 공용 일정 제안. 관리자는 요청 승인/반려.
*   **UI 배치**: 설정 항목별 폼과 제출 버튼 제공. 파괴적 행동(계정 삭제, 게임 구독 취소 등) 시 뚜렷한 그림자/테두리가 들어간 모달창(다이얼로그)으로 필수 재확인을 거칩니다.

## 2. 핵심 기능 간 유기적 연결 및 구현 통제 (Implementation Constraints)

에이전트는 기능을 임의의 방법으로 분리 구현해서는 안 되며, 아래의 데이터 연결 원칙(Domain Connection)을 엄격하게 지켜야 합니다.

### 2.1 지출 상태 전이의 원자성 (RPC 전용 조작 필수)
*   **연결점**: 예정 지출(PLANNED)이 결제 확정(CONFIRMED)이 될 때 단순 지출 상태만 바뀌는 것이 아닙니다. 
*   **통제 규칙**: `process_expense_payment` 등 전용 RPC를 통해 **지출 상태 변경 + 포인트 잔액 차감/적립(EARN/USE) + 자산 차감(deduct)** 세 가지가 DB 트랜잭션 내에서 한 번에 원자적으로 처리되어야 합니다. UI에서 클라이언트 단 `update` 쿼리를 여러 번 날려 각각 수정하는 행위는 절대 금지됩니다. (환불 역시 전용 RPC 사용)

### 2.2 일정(Schedule) 변동에 따른 지출(Expense) 동기화
*   **연결점**: 관리자가 공용 픽업 일정을 늦추거나 단축하면, 해당 일정에 바인딩된 **예정 지출(PLANNED)**들도 함께 움직여야 합니다. 
*   **통제 규칙**: DB 트리거에 의해 예정 지출의 날짜들(`start_date`, `end_date`, `target_date`)이 동기화됩니다. 단, 이미 결제를 완료한 **확정 지출(CONFIRMED)**은 일정이 바뀌더라도 결제일이라는 과거 사실이 바뀌지 않도록 철저히 보호(유지)되어야 합니다.

### 2.3 예산 계산 도메인 일원화와 초과 경고
*   **연결점**: 지출 내역이나 예산이 바뀔 때마다 캘린더와 대시보드의 소진율 경고가 즉각 연동되어야 합니다.
*   **통제 규칙**: 클라이언트 측 도메인 계산 함수를 일원화하여, "예상 소진액 = 확정 + 예정액 (취소 제외)"을 산출합니다. 월 예산의 **80%에 도달하면 주의 표시**, **100%를 초과하면 위험 경고**를 띄우고 지출 조작 시 확인 모달(Confirm)을 띄웁니다. (적용 예산이 0원일 때는 예외 처리). 

### 2.4 만료된 지출(Expired Planned)과 강제 처리 로직
*   **연결점**: 목표 결제일(Target Date)이 'KST 오늘'을 지났는데 결제 확정되지 않은 항목은 **미해결 만료 항목**으로 분류됩니다.
*   **통제 규칙**: 온라인 상태(또는 오프라인에서 온라인 복귀 시) 앱 진입 시, 미해결 만료 항목이 하나라도 있으면 필수 처리 모달 창이 팝업됩니다. 1) 결제 확정, 2) 예정 취소, 3) 가능한 다음 일정으로 이동 중 하나를 강제 선택해야만 캘린더 사용을 계속할 수 있습니다. 시스템이 임의로 자동 삭제하지 않습니다.

### 2.5 템플릿 비활성화와 구독 회차 재생성 차단
*   **연결점**: 반복 결제되는 구독(Subscription) 템플릿의 당월 회차는 캘린더 진입 시 지연 생성(Lazy Generation)됩니다. (`template_id + billing_cycle`로 중복 방지).
*   **통제 규칙**: 템플릿을 비활성화하면, 아직 미결제 상태인 이번 달 예정 지출 행들은 자동 물리 삭제되지 않고 `TEMPLATE_DEACTIVATION` 사유로 강제 취소 상태가 됩니다. 이후 사용자가 변심해 재활성화하더라도, 이미 취소된 과거 회차들을 임의로 다시 복구시켜서는 안 됩니다.

### 2.6 오프라인 모드 제약
*   **연결점**: 네트워크가 끊어진 상태에서의 캐시 활용.
*   **통제 규칙**: 오프라인에서는 기존 유효 세션에 한해 데이터 읽기만 허용되며, 어떤 형태의 지출 조작(쓰기 대기열 큐잉 등)도 비활성화되어야 합니다. 인증이 만료되면 개인정보 캐시 화면 접근도 완벽히 차단됩니다.
