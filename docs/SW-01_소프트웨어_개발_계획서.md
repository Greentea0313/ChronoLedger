# 1. 개요

## 1.1 프로젝트 개요

**배경**

- 모바일·PC 수집형 게임 이용자는 여러 게임의 버전 업데이트·픽업(한정 모집) 일정을 게임별 공지·커뮤니티에서 따로 확인함.
- 과금 지출(패키지·월정액·버전 패스)은 일정과 연결되지 않아 "이번 달 픽업에 얼마를 쓸지"를 미리 계획하기 어렵고, 스토어 포인트·월 예산도 별도로 관리해야 함.
- 기존 가계부 앱은 게임 일정을, 게임 정보 사이트는 개인 지출을 다루지 않아 둘을 함께 보는 도구가 없음.

**제안 프로젝트: ChronoLedger(크로노레저)**

- 게임 일정 캘린더와 개인 지출 계획을 하나로 묶은 개인용 앱임. 공용 일정은 관리자가 관리하고, 사용자는 관심 게임·일정을 골라 지출을 계획·확정함.
- 하나의 Next.js 코드베이스를 정적 빌드해 웹/모바일 PWA와 Windows 데스크톱 앱(Tauri)으로 동시에 제공함. 서버는 두지 않고 Supabase(인증·DB·저장소)를 백엔드로 씀.
- 개발은 사람 1명(발주자·제품 책임자)과 AI 코딩 에이전트 8종으로 구성한 책임프로그래머 팀이 수행함(3장).

## 5.2 위험 관리

교재의 Boehm 위험 관리 절차에 따라 아래 5단계를 프로젝트 기간 내내 반복함.

- 위험 파악: 작업 배분(Run 등록) 때마다 교재의 10대 위험 요소를 기준으로 점검하고, 이 프로젝트에만 있는 위험을 추가함.
- 위험 분석: 손실 발생 확률과 손실 규모를 각각 3(높음)·2(중간)·1(낮음)로 매기고, 위험 노출 = 확률 × 규모로 계산함.
- 위험 우선순위 정하기: 위험 노출 값이 큰 순서로 정하고, 6 이상은 우선 관리 대상으로 둠.
- 위험 해결: 표의 대응 방안을 해당 Run의 수용 기준이나 별도 작업으로 반영함.
- 위험 모니터링: 주간 진도 점검과 검토회에서 우선 관리 대상의 상태를 확인하고, 새로 생긴 위험은 위험 파악 단계로 되돌림.

## 5.3 비용 및 진도 관리

**관리 방법**: 작업 배분표의 단계별 상태(대기 → 진행 가능 → 완료/차단)를 진도 기준으로 삼고, 매주 금요일 투입 MM과 완료 작업 수를 계획과 비교함. 계획 대비 10% 이상 지연되면 우선순위를 다시 정하거나 대체 인력을 추가함.

<!-- widths: 1500,2700,2526,2300 -->
| 단계 | 관리 기준 | 완료 조건(게이트) | 점검 방법 |
| :---: | :--- | :--- | :--- |
| 요구사항 분석 | 기능 목록·수용 기준 확정 비율 | SRS 사용자 승인 | 요구사항 검토회(11/25) |
| 설계 | 스키마·화면 설계 완료 비율, 결정 대기 항목 수 | 설계 검토회 승인, 미결정 항목 0건 | 설계 검토회(11/30) |
| 구현 | Run 완료 수, 투입 MM 대비 진척, 리뷰 지적 잔여 수 | 각 Run의 리뷰 P1·P2 지적 0건, 테스트 통과 | 주간 점검, 중간 검토회(12/7) |

[표 5-4] 단계별 비용·진도 관리

- 비용은 인력별 투입 MM으로 관리함. 상위 인력(Argon·Opus)은 사용량 주기가 길어 고위험 작업에만 배정하고, 일반 작업은 기본 인력에 몰아 비용을 아낌.

## 5.4 문제점 해결 방안

- 대체 인력까지 모두 한도에 걸린 경우: 작업을 중단 체크포인트로 저장하고 한도가 풀릴 때까지 해당 작업만 보류함. 다른 독립 작업을 먼저 진행해 일정 손실을 줄임.
- AI 간 규칙 해석 차이: 공통 규칙을 한 곳(협업 규칙·Skill 문서)에만 두고, 다른 문서는 참조만 하게 해 내용이 엇갈리지 않게 함.
- 운영 DB 반영 누락: 마이그레이션은 사용자가 수동 적용하므로, 앱은 새 컬럼이 없을 때도 동작하도록 대체 조회를 두고 반영 여부 확인 쿼리를 문서에 남김.
- 외부 서비스 정책 변경: 무료 플랜 한도·중지 정책이 바뀌면 유지보수 주기에 비용·대안을 재검토함.
- 로컬 시험 환경 부재: Docker 등 DB 시험 환경이 없는 PC에서는 SQL을 작성만 하고 "미실행"으로 기록해 다음 검토 단계에서 반드시 실행함.

## 7.2 검토회 진행 방법

- 사전 배포: 검토 대상 문서·커밋 범위·수용 기준을 2일 전에 인수인계 문서에 올림.
- 정적 검토: 검토자는 대상 커밋을 고정하고 근거(파일·행)를 들어 지적함. 지적은 P1(치명)~P4(개선 제안)로 나눔.
- 회의 진행: 지적 사항 설명 → 담당 Maker 의견 → 처리 방향 결정. 제품 결정이 필요한 항목은 사용자에게 질문 카드로 묻고 결정을 받음.
- 판정: 승인 / 조건부 승인(지적 반영 후 확인) / 재검토 중 하나로 정함.
- 기록: 검토 결과를 review.json·test.json과 인수인계 문서 완료 기록에 남김.

# 11. 유지보수

- 요청 접수: 사용자는 앱 안의 기타 건의(기능 제안·오류 신고) 창구로 요청하고, 관리자 답변은 앱 내 알림으로 전달됨.
- 분류와 처리: 수정(결함), 적응(외부 서비스·브라우저 변화 대응), 완전(기능 개선), 예방(구조 정리)으로 나눠 할 일 목록에 R번호로 등록하고 Run으로 처리함.
- DB 변경: 마이그레이션을 재실행 가능하게 작성하고, 운영 적용 후 확인 쿼리로 결과를 검증함.
- 정기 점검: 분기마다 의존성(Next.js·Supabase·Tauri) 업데이트와 무료 플랜 한도를 점검함.

# 12. 설치, 인수

**설치 절차**

- Supabase 프로젝트 생성 → SCHEMA.sql 적용 → 비공개 아이콘 저장소 생성 → 게임 시드 적용 → 관리자 계정 지정.
- 웹: 환경 변수(Supabase URL·공개 키) 설정 후 정적 빌드를 Cloudflare Pages에 배포함. 모바일은 브라우저 메뉴의 "홈 화면에 추가"로 설치함.
- 데스크톱: Tauri로 빌드한 Windows 설치 파일을 실행하고 딥링크 로그인을 확인함.

**인수 절차**

- SRS 수용 기준별 인수 시험 체크리스트로 사용자가 실제 화면에서 확인함(가입·일정·지출·결제·환불·구독·포인트·요청·오프라인).
- 인수 조건: 치명·중요 결함 0건, 전체 테스트 통과, 산출물 7종(1.2절) 제출.
- 인수 검토회(12/18)에서 사용자가 승인하면 운영으로 이관하고 유지보수 단계로 넘어감.
