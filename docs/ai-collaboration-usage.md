# AI 협업 사용 안내 (초보자용)

이 문서는 Maker, Reviewer, Orchestrator 역할을 맡은 AI를 사용해 한 작업을 만들고 서로 확인하는 방법을 설명한다. 현재 역할 간 자동 호출은 설정되어 있지 않으므로, 사람이 프롬프트와 파일을 전달하며 진행한다.

## 먼저 알아둘 말

- **저장소(repository)**: 프로젝트 파일과 변경 기록을 보관하는 Git 프로젝트.
- **커밋(commit)**: 특정 시점의 파일 변경을 식별하는 저장 기록. 긴 해시 중 앞부분으로도 보통 구분할 수 있다.
- **브랜치(branch)**: 다른 작업과 변경을 분리하는 이름 있는 작업 흐름.
- **worktree**: 한 저장소 안에서 별도 폴더에 브랜치를 체크아웃해 독립적으로 작업하는 기능. 이 협업 흐름에서는 원래 프로젝트 작업 폴더를 보호하는 격리 공간이다.
- **run**: 목표, 기준 커밋, 반복 횟수와 AI들의 결과를 묶어 기록하는 한 번의 협업 작업.
- **수용 기준**: 완료 여부를 판단할 수 있는 구체적인 조건.
- **SHA**: 커밋을 가리키는 Git 식별자. Maker, Reviewer, Orchestrator가 같은 Target SHA를 기준으로 결과를 맞춰야 한다.

## 역할 배정

| 역할 | 담당 | 하는 일 | 하지 않는 일 |
|---|---|---|---|
| Maker | Codex 등 구현 AI | 요청된 코드 변경, 자체 확인, 변경 커밋 생성 | 범위를 벗어난 결정을 사용자 대신 내리지 않음 |
| Reviewer | Gemini Code Assist 등 검토 AI | Base와 Target 변경을 읽고 문제 및 근거를 기록 | 파일을 수정하거나 결과를 다수결로 판정하지 않음 |
| Orchestrator | Gemini Spark 등 조정 AI 또는 사용자 | 격리 환경에서 검증을 실행하고 결과를 모아 상태를 정리 | 프로젝트 코드를 수정하거나 호스트에서 임의로 위험한 명령을 실행하지 않음 |

제품이나 계정에서 특정 AI를 사용할 수 없다면 해당 역할을 다른 AI나 사람이 맡을 수 있다. 중요한 점은 역할을 구분하고 각 역할의 결과를 파일로 남기는 것이다.

## 작업 순서

### 1. 목표와 완료 조건을 정한다

작업은 작고 검증 가능하게 적는다. 예를 들어 “환불 기능을 개선한다” 대신 다음처럼 쓴다.

- 목표: 환불 RPC가 포인트와 자산 원장을 정확히 복원하는지 확인한다.
- 완료 조건: 성공하면 잔액과 원장이 일치한다.
- 완료 조건: 실패한 환불은 데이터 변경을 남기지 않는다.

프로젝트 문서 지침에 따라 세션을 시작할 때 `md/SKILL.md`, `md/agent_rules.md` 및 작업과 관련된 기획 문서를 확인한다. 현재 결정과 요구사항은 구현 전에 관련 문서와 맞춘다.

### 2. 실행 전 저장소 상태를 확인한다

PowerShell에서 저장소 폴더로 이동한 뒤 다음 명령으로 변경 상태를 본다.

```powershell
git status --short
```

실행 준비 스크립트는 추적 중인 파일뿐 아니라 새로 생긴 파일까지 포함해 작업 폴더가 깨끗한지 확인한다. 변경이 남아 있으면 자동으로 숨기거나 복사하거나 버리지 않고 중단한다. 현재 작업을 검토해 보존한 뒤, 프로젝트의 Git 절차에 맞게 커밋하여 깨끗한 상태를 만든다. 사용자 변경을 확인 없이 폐기하지 않는다.

### 3. 전용 run과 작업 공간을 만든다

저장소 루트에서 아래 형식으로 실행한다.

```powershell
.\scripts\collaboration\New-CollaborationRun.ps1 `
  -RunId "expense-refund-review" `
  -Objective "환불 처리의 잔액과 원장 반영을 검토한다" `
  -AcceptanceCriteria @(
    "환불 성공 후 지갑 잔액과 원장이 일치한다",
    "환불 실패 시 데이터 변경이 남지 않는다"
  )
```

`RunId`는 고유한 소문자 영문/숫자/하이픈 이름으로 정한다. 이 명령은 `.worktrees/<RunId>`에 전용 worktree와 `collab/<RunId>` 브랜치를 만들고 `artifacts/<RunId>/run.json`을 생성한다. 이미 같은 이름이 있으면 다른 RunId를 쓴다. 선택적으로 `-BaseRef`로 기준 커밋을, `-MaxIterations`로 반복 한도를 지정할 수 있으며 한도는 1~3회다.

스크립트가 실패하면 오류 내용을 확인하고 원인을 해결한다. 특히 작업 폴더가 깨끗하지 않다는 오류는 변경을 저장/보존해야 한다는 뜻이다. 이를 우회하려고 파일을 지우거나 강제 초기화하지 않는다.

### 4. Maker가 격리 공간에서 구현한다

Maker에게 `run.json`의 목표와 수용 기준을 전달한다. 반드시 `.worktrees/<RunId>` 안에서 작업하도록 하고, 끝나면 변경 요약과 수행한 확인을 요청한다. Maker가 실제 변경을 커밋한 뒤 그 커밋의 SHA를 확인한다.

`artifacts/<RunId>/run.json`의 `target_sha`는 스크립트가 처음 만들 때 `null`이다. Maker 커밋이 끝난 후 Reviewer와 Orchestrator가 검사할 정확한 커밋 SHA로 업데이트한다. 이때 두 역할 모두 같은 Target SHA를 사용한다.

### 5. Reviewer에게 정적 검토를 맡긴다

Reviewer에게 Base SHA와 Target SHA 사이의 변경, 필요한 관련 파일, 수용 기준을 전달한다. 읽기 전용으로 검토하고 결과를 `artifacts/<RunId>/iteration-01/review.json`에 기록하도록 요청한다. 결과 형식은 `artifacts/schemas/review.schema.json`과 `artifacts/templates/review.example.json`을 참고한다.

각 발견 사항은 파일, 줄, 근거, 영향, 권장 조치를 포함해야 한다. 문제가 없으면 근거와 검토 범위를 명시한 빈 발견 목록을 기록한다. 파일을 직접 고치게 하지 않는다.

### 6. Orchestrator가 격리 환경에서 시험한다

Orchestrator에게 같은 Target SHA, 수용 기준, 프로젝트의 시험 지침을 전달한다. 동적 테스트는 Docker 등 호스트와 격리된 환경에서만 실행한다. 운영용 `.env`나 실제 사용자 데이터를 사용하지 않는다. 현재 Docker를 사용할 수 없으면 실행한 것처럼 결과를 만들지 말고 `blocked` 또는 `not_run` 상태와 이유를 기록한다.

결과는 `artifacts/<RunId>/iteration-01/test.json`에 기록하고 `artifacts/schemas/test.schema.json`, `artifacts/templates/test.example.json` 형식을 따른다. 민감한 값이나 원본 로그를 결과 파일에 넣지 않는다.

### 7. 결과에 따라 마무리하거나 한 차례 수정한다

- Reviewer와 테스트가 모두 수용 기준을 만족하면 결과를 확인하고 사용자용 요약을 남긴다.
- 수정이 필요하면 Reviewer의 근거와 시험 결과를 Maker에게 전달한다. Maker가 수정 후 새 커밋을 만들면 `target_sha`를 새 SHA로 갱신하고 다음 반복 폴더에서 리뷰와 테스트를 다시 수행한다.
- 반복은 run에 정한 최대 횟수(최대 3회)까지만 한다. 해결되지 않은 P1 보안/데이터 무결성 문제나 결과 간 충돌은 임의로 성공 처리하지 말고 사용자에게 보고한다.
- 중단 시 `artifacts/templates/human-report.md`를 참고해 문제, 근거, 선택지를 간결하게 정리한다.

## 꼭 지킬 안전 규칙

- Maker만 구현하며 Reviewer와 Orchestrator는 코드를 고치지 않는다.
- 세 역할의 판정 대상은 동일한 커밋 SHA여야 한다.
- 작업은 run 전용 worktree에서 한다. 공유 프로젝트 작업 폴더에서 동시에 수정하지 않는다.
- 자동 `git reset --hard`를 실행하지 않는다. 실패한 브랜치와 worktree를 검토할 수 있도록 보존한다.
- 비밀번호, 토큰, 개인정보, 운영 `.env`, 마스킹되지 않은 로그를 공유 아티팩트에 저장하지 않는다.
- 실제로 수행하지 않은 빌드나 테스트를 통과했다고 보고하지 않는다.
- 현재 AI 간 자동 연결은 설정되어 있지 않다. 프롬프트 전달과 아티팩트 파일 작성은 수동으로 해야 한다.

## 이 프로젝트에서 아직 확인되지 않은 점

- 실행 준비 스크립트는 구문 검토만 되었고, 실제 새 worktree와 manifest 생성 흐름은 아직 동작 검증되지 않았다.
- 현재 환경에는 Docker가 확인되지 않아 컨테이너 테스트를 실행할 수 없다.
- Gemini AI가 같은 로컬 파일을 직접 읽고 쓰도록 연결되어 있지 않다. 사용 가능한 제품 기능에 따라 파일을 직접 전달해야 한다.

세부 파일 규약과 격리 정책은 [아티팩트 안내](../artifacts/README.md), 역할 설계는 [협업 아키텍처](../md/multi_agent_collaboration_architecture.md)를 참고한다.
