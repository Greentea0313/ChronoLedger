# ChronoLedger 기획 문서 검토

상태 전이, 일정-지출 동기화, 만료 처리 같은 **"이미 있는 데이터가 바뀔 때"의 규칙**은 꼼꼼합니다. 반면 **데이터가 처음 생기는 경로(생성 UI)**와 **결과를 보여주는 경로(표시 UI)**가 비어 있는 곳이 많습니다. 이대로 구현하면 에이전트가 그 빈칸을 임의로 채울 가능성이 높습니다.

---

## 1. 유기적으로 연결되지 않아 버려질 위험이 있는 부분

**① 예정 지출(PLANNED)의 생성 경로가 없음**
- 문서는 PLANNED가 확정, 취소, 이동되는 규칙만 다루고, 어떻게 만들어지는지는 없습니다.
- 픽업 일정에서 "가계부에 추가"로 생기는지, `/expenses`에서 수동 입력하는지, 즉시 확정 지출(PLANNED를 거치지 않는 것)이 있는지 불명확합니다.
- 일정 변동 시 동기화되는 지출은 "일정에 바인딩된" 것인데, 바인딩이 생기는 시점과 화면이 정의되어 있지 않습니다.

**② 캘린더 타일 제한과 경고 연동의 충돌**
- 2.3은 "캘린더와 대시보드의 소진율 경고가 즉각 연동"된다고 하지만, 1장은 타일에 아이콘, 배너, 메모 도트만 허용합니다.
- 그러면 **PLANNED 결제 예정일, 만료 항목, 예산 초과**가 달력 위에서 보이지 않습니다. 사용자는 날짜를 눌러야만 알 수 있어, 예정 지출이 캘린더와 사실상 분리됩니다.
- 금액 없이 "결제 예정" 마커 하나를 허용하는 식으로, 제한을 깨지 않는 연결 방식이 필요합니다.

**③ 포인트와 지갑이 표시되는 곳이 없음**
- RPC는 포인트를 EARN/USE로 처리하지만, 결제 확정 시 포인트 사용 여부와 금액을 입력하는 UI가 정의되어 있지 않습니다.
- 포인트 잔액, 이력, 자산 잔액을 보는 화면도 없습니다. 설정의 "잔액 보정"만 있어서 쌓이기만 하고 보이지 않는 데이터가 됩니다.
- 자산 부족 시 동작도 없습니다(음수 허용, 차단, 경고 중 무엇인지).
- "자산"이 복수인지 단일인지, "예산"과 어떤 관계인지도 모호합니다.

**④ 환불의 결과 상태가 없음**
- 상태는 CONFIRMED, PLANNED, CANCELLED 세 가지인데 기능에는 "환불"이 있습니다. 환불된 지출이 어떤 상태가 되는지, 예산 계산("확정+예정, 취소 제외")에서 어떻게 취급되는지 알 수 없습니다.
- 전액 환불만 지원하는지, 포인트 적립분도 회수하는지, 다른 달에 환불하면 어느 달 예산에서 빼는지 정해져야 합니다.

**⑤ 게임 구독 취소가 기존 지출을 고아로 만들 수 있음**
- 내 게임 구독을 취소하면, 해당 게임 일정에 바인딩된 내 PLANNED 지출은 어떻게 되는지 정의가 없습니다. 유지, 자동 취소, 취소 불가 중에서 정해야 합니다.
- 게임 자체(카탈로그)를 누가 추가하고 관리하는지도 없습니다. `/admin`에는 요청 승인/반려만 있습니다.

**⑥ 일정 제안 요청의 사용자 측 피드백이 없음**
- 사용자가 제안한 뒤 승인/반려 결과를 어디서 확인하는지 없습니다. 제안 유형(신규, 수정, 삭제)도 구분되어 있지 않습니다.
- 승인된 수정이 사용자의 PLANNED 지출 날짜를 **조용히 바꾸므로**, 변경 알림 없이는 예산 경고가 갑자기 바뀌어 사용자가 혼란스러울 수 있습니다.

**⑦ 구독 템플릿의 생성과 편집 화면이 없음**
- 템플릿을 비활성화하는 규칙은 상세하지만, 만드는 화면(설정, 가계부 등)과 필드가 없습니다.
- 템플릿 금액을 수정하면 이번 달 PLANNED 회차에 반영되는지도 정의가 없습니다.
- 구독 스토어 적립률(지갑)과 템플릿의 연결 방식도 불명확합니다.

**⑧ 메모의 작성/편집 경로가 없음**
- 대시보드는 메모를 보여주기만 합니다. 어디서 작성, 수정, 삭제하는지, 날짜 단위인지 지출에 붙는지, 오프라인에서 읽기 전용이 되는지 정의가 필요합니다.

**⑨ 통계가 가계부로 이어지지 않음**
- 통계에서 막대를 눌렀을 때 해당 필터로 `/expenses`에 이동하는 연결이 없으면 독립된 읽기 전용 화면이 됩니다.
- 집계 대상도 정의가 없습니다. CONFIRMED만인지 PLANNED 포함인지, 환불 반영 여부, 포인트 사용분을 지출로 볼지가 정해져야 합니다.

## 2. 더 구체화가 필요한 부분

**지출 데이터 모델**
- 핵심 필드(금액, 통화, 게임, 결제 플랫폼, 카테고리, 결제일, 목표일, 메모)와 필수/선택이 없습니다. 통계의 "결제 플랫폼별"이 이 필드에 의존합니다.
- 통화가 KRW 고정인지 외화(JPY, USD 등)와 환율을 지원하는지도 정해야 합니다.

**만료 처리 모달 (2.4)**
- "다음 일정으로 이동"할 일정이 없을 때의 대체 동작이 없습니다. 구독 회차는 애초에 일정이 없으므로 선택지가 달라야 합니다.
- 만료 항목이 여러 개일 때 순차 처리인지 일괄 처리인지, 모달 중에도 설정이나 로그아웃은 접근 가능한지 정해야 합니다.
- 만료 후 확정할 때 **결제일을 오늘로 할지 목표일로 할지**와, 그 금액이 어느 달 예산에 잡히는지가 비어 있습니다.

**예산 (2.3)**
- "적용 예산"이라는 표현은 기본 예산과 월별 오버라이드가 있다는 암시인데, 정의가 없습니다.
- 확인 모달이 뜨는 조작 범위가 불분명합니다(생성, 확정, 이동 중 어느 것인지). 서버(RPC)는 초과를 막지 않고 클라이언트 확인만 하는 구조가 의도된 것인지도 명시가 필요합니다.

**일정 동기화 (2.2)**
- 단축된 일정의 `end_date`가 기존 `target_date`보다 앞서게 되면 어떻게 보정하는지 정해야 합니다.
- 일정이 삭제되거나 취소될 때의 처리도 없습니다. 취소 사유 코드(`SCHEDULE_REMOVED` 등)가 필요해 보입니다.

**템플릿 재활성화 (2.5)**
- 이번 달 회차가 이미 TEMPLATE_DEACTIVATION으로 취소된 상태에서 재활성화하면 이번 달은 영구히 비는 셈입니다. 의도라면 사용자에게 안내하는 문구가 필요하고, 아니라면 규칙을 다시 정해야 합니다.
- 지연 생성의 범위(이번 달만인지 미래 달 조회 시 생성하는지)도 정해야 합니다.

**오프라인 (2.6)**
- 대시보드 외에 `/expenses`, `/statistics`, `/settings`는 오프라인에서 읽기 가능한지 명시가 없습니다.
- 캐시가 오래됐음을 알리는 표시, 로그아웃 시 캐시 삭제, 만료 모달이 오프라인 복귀 시 어느 시점에 뜨는지도 필요합니다.

**인증과 플랫폼**
- 비밀번호 재설정, 이메일 인증, 계정 삭제 시 데이터 처리(지출, 포인트, 템플릿 일괄 삭제 여부)가 없습니다.
- Tauri에서의 Google OAuth(PKCE 리다이렉트/딥링크 처리)가 PWA와 다를 텐데 분리 설명이 없습니다.
- 관리자 권한 부여 방식과 `/admin` 접근 차단(비관리자 리다이렉트)도 정해야 합니다.

**레이아웃과 내비게이션**
- 전체 내비게이션(사이드바, 하단 탭), 로그인 후 기본 진입 화면, 로딩/빈 상태/에러 상태가 없습니다.
- 모바일에서는 예산 패널이 바텀 시트 안에 들어가는지 별도 영역인지 불명확합니다(데스크톱만 우측 사이드바로 기술됨).

**동시성**
- 확정 버튼 중복 클릭이나 다른 기기에서 이미 상태가 바뀐 지출에 대한 RPC 멱등성과 충돌 시 안내가 없습니다. 2.1이 원자성을 강조하는 만큼 같이 정의하는 것이 좋습니다.

---

## 3. 문서 내부의 모순 후보

- 1장은 "금액을 타일에 표기하지 않음"인데, 2.3은 캘린더 단의 소진율 경고를 요구합니다(위 ②).
- 상태 목록에 환불이 없는데 기능에는 환불이 있습니다(위 ④).
- 대시보드 기능에 "예산 소진 현황"이 있는데, 모바일 레이아웃 설명에는 예산이 빠져 있습니다.

---

## 4. 우선 결정이 필요한 항목 (구현 착수 전)

1. PLANNED 지출의 생성 경로와 화면
2. 환불 시 상태, 예산, 포인트 처리
3. 지출 필드 정의와 포인트/자산 UI (결제 확정 시 입력, 잔액 표시 위치)
4. 캘린더 타일의 결제 예정/만료 마커 허용 여부
5. 게임 구독 취소 시 기존 PLANNED 처리
6. 일정 변경과 제안 결과의 사용자 알림 방식

이 6개가 정해지지 않으면 에이전트가 가장 임의로 구현하기 쉬운 부분이 됩니다.
