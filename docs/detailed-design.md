# 시스템 상세 설계

- 상태: 설계 기준 초안
- 기준: 승인된 [SRS v1.0](../md/SRS.md), [기능 명세](../md/SPEC.md), [통합 결정](../md/revisions_and_decisions.md), [DB 스키마 초안](../md/SCHEMA.sql)
- 상위 구조와 모듈 책임: [architecture.md](architecture.md)
- 설계 원칙: 이 문서는 승인된 요구사항과 스키마 계약을 구현 가능한 흐름으로 연결한다. 기준 문서에 없는 기술 선택은 확정하지 않고 §10에 미결정으로 남긴다.

## 1. 범위와 기준

승인된 SRS의 제품 범위와 상위 구현 방향은 유지한다: 단일 Next.js 코드베이스에서 Android PWA와 Windows Tauri v2를 제공하고, Tauri 프런트엔드는 정적 export를 사용한다. 사용자는 Android PWA 실기기 검증을 미루고 웹사이트 개발을 우선하기로 했다. 이는 Android 제품 범위를 취소하지 않는다. 모바일·데스크톱 앱의 구체 릴리스 버전 번호 및 릴리스 시점/구성은 미결정으로 둔다. 사용자는 Netlify를 웹 호스팅 후보로 고려하고 있으며, 우선 검증은 현재 정적 export를 Netlify에서 제공하는 최소 경로다. Netlify 채택 및 Web/Desktop 빌드 분리는 Deploy Preview 검증 전까지 확정하지 않는다. 제품 동작은 SRS를 우선하고, 데이터 제약과 RPC 이름/인자는 `SCHEMA.sql`을 기준으로 한다.

사용자는 이 앱을 과제 제출물이 아닌 개인 프로젝트로 진행하기로 결정했다. 따라서 과제 요구사항(SQLite, 별도 Node.js 웹서버, 게시판)은 범위에 추가하지 않으며, 승인된 Supabase PostgreSQL·정적 export 및 기존 회원/관리자 요구사항을 유지한다. 이는 Netlify나 상시 실행 Node.js 서버 채택을 의미하지 않는다.

이 설계는 브라우저 클라이언트가 Supabase SDK로 인증, RLS 보호 조회, 허용된 변경 및 RPC를 호출하는 구성을 전제로 한다. 비밀 키를 사용하는 서버 API는 현재 확정된 구성요소가 아니다. 승인된 SRS, SPEC 또는 SCHEMA와 이 문서가 충돌하면 기준 문서를 따른다.

## 2. 런타임 경계와 의존 방향

```text
Web client (app version/packaging TBD)
┌─────────────────────────────────────────────────────────────┐
│ Route / UI                                                  │
│  인증 · 캘린더 · 지출 · 지갑 · 설정 · 요청 관리            │
│                         │                                   │
│                         ▼                                   │
│ Feature services / domain rules                             │
│  예산 귀속 · 날짜 계산 · 상태별 명령 · 아이콘 변환          │
│                         │                                   │
│                         ▼                                   │
│ Supabase browser client                                     │
│  Auth · RLS table query · RPC · private Storage             │
└─────────────────────────┬───────────────────────────────────┘
                          │ public client key + user session
                          ▼
┌─────────────────────────────────────────────────────────────┐
│ Supabase                                                    │
│ Auth → PostgreSQL(RLS, constraints, triggers, RPC)          │
│      └→ private Storage(user-icons, owner-scoped policies)   │
└─────────────────────────────────────────────────────────────┘
```

- UI는 폼 상태와 표시를 담당하고 금액 확정, 상태 전이, 소유권 판단을 신뢰할 수 있는 클라이언트 검증으로 대체하지 않는다.
- 도메인 계산은 순수 함수로 분리해 예산 귀속, KST 날짜, 말일 보정 등 반복 규칙을 단위 테스트한다.
- feature service는 화면이 직접 Supabase 쿼리 문자열을 조립하는 것을 줄이고, 쿼리/RPC 입력과 오류 경계를 한 곳에 둔다. 실제 디렉터리·함수 이름은 구현 시 코드 구조에 맞춰 정한다.
- DB constraints/RPC가 회계 불변성과 권한의 최종 집행자다. Supabase RLS가 행 소유권을 다시 제한한다.
- 승인된 SRS에는 별도 애플리케이션 서버가 정의되어 있지 않다. 계정 삭제처럼 권한 있는 서버 작업이 필요한 흐름은 §10의 결정을 먼저 완료해야 한다.

## 3. 도메인 데이터와 소유권

상세 컬럼, 외래 키, 제약, 인덱스는 [SCHEMA.sql](../md/SCHEMA.sql)의 단일 기준을 사용한다. 이 절은 데이터 책임만 요약한다.

| 데이터 그룹 | 테이블 | 책임 / 접근 경계 |
|---|---|---|
| 개인 재무 | `user_finances`, `monthly_budgets` | 사용자 자산, 기본 예산, 월별 예산. 재무 변경은 `set_user_finance_settings` 경로를 사용한다. |
| 공용 게임·일정 | `games`, `game_schedules` | 승인된 카탈로그와 VERSION/PICKUP 일정. 인증 사용자 읽기, 관리 작업은 관리자 경로. |
| 사용자 게임·요청 | `user_games`, `game_requests`, `schedule_requests` | 개인 구독/아이콘 경로, 관리자 승인 전의 제안 행. |
| 캘린더·회계 | `personal_memos`, `expenses`, `subscription_templates` | 개인 메모, 예정/확정/취소 지출, 반복 지출 템플릿. 지출 물리 삭제 금지. |
| 스토어 지갑·감사 원장 | `store_wallets`, `store_point_transactions` | 플랫폼별 잔액과 불변 감사 내역. 사용자 직접 쓰기는 차단하고 RPC만 변경한다. |
| 비공개 파일 | Supabase Storage `user-icons` | `{user_id}/{game_id}.webp` 소유자 경로. public URL은 사용하지 않는다. |

공통 불변 조건:

- 사용자 개인 행은 `auth.uid() = user_id` RLS로 격리한다. 클라이언트가 보낸 사용자 ID를 권한 근거로 삼지 않는다.
- 관리자는 JWT의 서버 관리 `app_metadata.role=admin`으로 판정한다. 클라이언트가 이 값을 설정할 수 없다.
- 금액은 KRW 정수, 날짜 전용 값은 `DATE`, 생성/수정 시각은 UTC `TIMESTAMPTZ`를 사용한다. KST 오늘 판정은 서버 규칙과 일치시킨다.
- 공용 일정 종류는 `VERSION`/`PICKUP`뿐이다. 연결 일정이 변경될 때 DB 트리거가 `PLANNED` 지출만 동기화하고 `CONFIRMED` 회계 값은 보존한다.
- 동일 템플릿/청구 월은 `(template_id, billing_cycle)` 부분 유니크 인덱스로 멱등성을 보장한다.

## 4. 애플리케이션 인터페이스

### 4.1 읽기 계약

화면은 인증 세션을 확인한 뒤 Supabase SDK로 필요한 데이터를 조회한다. 조회 대상은 사용자 게임 및 아이콘 경로, 해당 월의 일정/메모/지출, 재무/예산, 지갑, 요청 상태 등이다. 각 조회는 로그인 사용자 RLS 범위에 맡기며 타 사용자 데이터나 관리자 전용 데이터를 클라이언트에서 합성하지 않는다.

예산 화면, 캘린더 상세 및 경고는 동일한 월 귀속 기준을 사용한다.

- `CONFIRMED`: 결제일(`target_date`)이 속한 달.
- `PLANNED`: `end_date`가 있으면 종료일, 없으면 `target_date`가 속한 달.
- `CANCELLED`: 합계에서 제외.
- 월별 예산이 없거나 0이면 기본 예산을 적용하고, 최종 예산이 0이면 비율 경고와 초과 확인을 표시하지 않는다.

예산 집계는 공유 클라이언트 도메인 함수에서 계산한다. 온라인에서는 RLS가 적용된 해당 기간의 지출/예산 행을 입력으로 사용하고, 오프라인 허용 읽기에서는 사용 가능한 캐시 데이터만 같은 함수에 입력한다. 캐시에 없는 데이터를 완전한 집계 결과처럼 표시하지 않으며 조회 범위·누락 데이터 표시는 별도 오프라인 계약에 따른다. 계산 규칙은 §4.1에 단일화한다.

Dashboard의 당월 예정 지출도 동일한 `PLANNED` 월 귀속 날짜를 사용한다. PostgreSQL `DATE` 컬럼은 KST에서 산출한 `YYYY-MM-01`부터 다음 달 `YYYY-MM-01` 전까지 반개구간으로 조회하고, `end_date`가 없을 때만 `target_date`를 적용한다. 정상 빈 결과는 0원이며, 조회 실패 또는 재무 행 누락은 별도 오류 상태로 표시한다.

### 4.2 쓰기 계약

일반 테이블 쓰기는 스키마가 허용한 범위에서만 수행한다. 예정 지출 생성/수정은 `PLANNED` 상태와 회계 필드 제약을 지키며, 결제 확정·환불·취소·복구·지갑 변경·관리자 승인은 아래 RPC를 사용한다. RPC 이름/인자 순서는 실제 스키마와 일치시킨다.

| 명령 | RPC와 입력 | 기대 결과 |
|---|---|---|
| 결제 확정 | `process_expense_payment(p_expense_id, p_original_price, p_discount_amount, p_point_discount_amount, p_used_points, p_point_platform, p_payment_method, p_deduct_asset, p_payment_date)` | 인증 사용자 소유의 `PLANNED`만 처리한다. 할인 산식, 포인트/결제 플랫폼, 잔액, 미래 결제일을 검증하고 지출·자산·지갑·원장을 한 트랜잭션으로 갱신한다. |
| 결제 환불 | `refund_expense_payment(p_expense_id)` | `CONFIRMED`만 환불한다. 포인트 복원/회수 가능성과 자산 복원을 검증한 뒤 `PAYMENT_REFUND`로 취소한다. 적립분 잔액이 부족하면 전체 롤백한다. |
| 예정 취소 / 복구 | `cancel_planned_expense(p_expense_id)`, `restore_cancelled_expense(p_expense_id)` | 사용자 소유 및 허용 상태 전이를 검증한다. 환불 상태는 복구할 수 없다. 템플릿 비활성화 취소 회차는 템플릿이 다시 활성 상태일 때만 복구한다. |
| 재무 설정 | `set_user_finance_settings(p_total_asset, p_default_budget)` | 서버에서 사용자 행을 갱신/생성한다. 자산 음수는 허용하고 기본 예산 음수는 거부한다. |
| 지갑 설정 / 잔액 보정 | `update_store_wallet_settings(p_platform, p_tier, p_earn_rate)`, `adjust_wallet_balance(p_platform, p_target_balance, p_memo)` | 플랫폼별 유효 등급/적립률을 검증한다. 잔액 보정은 `MANUAL_ADJUST` 원장을 남긴다. |
| 게임 요청 승인/반려 | `approve_game_request(p_request_id, p_default_icon_url)`, `reject_game_request(p_request_id, p_admin_memo)` | 관리자만 수행. 게임 승인과 요청 상태 전환은 원자적이며 요청자의 `user_games` 행을 자동 만들지 않는다. |
| 일정 요청 승인/반려 | `approve_schedule_request(p_request_id)`, `reject_schedule_request(p_request_id, p_admin_memo)` | 관리자만 수행. 일정 반영과 요청 상태 전환은 원자적이며, 일정 날짜 변경 시 DB 트리거가 관련 예정 지출을 동기화한다. |

UI는 RPC 호출이 성공하기 전 회계 작업을 완료 상태로 표시하지 않는다. 실패하면 서버 상태를 다시 읽어 표시를 정합화하며, 오류를 성공 모양의 기본값으로 숨기지 않는다.

## 5. 핵심 사용자 흐름

### 5.1 인증 및 세션 경계

1. 비인증 사용자는 로그인/가입 화면에서 이메일 또는 Google 인증을 시작한다.
2. 브라우저 Google OAuth는 PKCE를 사용한다. 공급자 redirect의 `code`는 `/auth/callback`에서 `exchangeCodeForSession`으로 교환한다. callback 오류·취소·코드 누락·교환 실패는 사용자가 재시도할 수 있는 오류 화면을 제공한다.
3. 세션이 확인되면 보호 화면으로 이동하고 개인 데이터 조회를 시작한다. 초기 세션 판정 중에는 개인 데이터를 렌더링하지 않는다.
4. 로그아웃/세션 만료 시 세션과 개인 데이터 표시를 즉시 차단한다. 캐시가 있더라도 유효 세션이 확인되지 않으면 개인정보를 렌더링하지 않는다.
5. Tauri callback/deep-link 구현은 후속 플랫폼 작업이다. 브라우저 PKCE 계약에 Tauri scheme 동작을 섞지 않는다.

### 5.2 월간 캘린더 및 예산 표시

1. 인증 후 선택 월의 공용 일정과 개인 게임/메모/지출/예산 데이터를 조회한다.
2. 공용 VERSION/PICKUP 일정은 해당 날짜 범위의 배너로 표현하고, 개인 메모는 날짜별 개수와 무관하게 도트 하나로 표현한다. 타일에는 금액이나 일반 지출 목록을 렌더링하지 않는다.
3. 날짜 선택 시 데스크톱 상세 사이드바 또는 모바일 바텀 시트에 상세 일정, 모든 해당 날짜 메모, 지출 정보를 표시한다.
4. 예산 요약은 §4.1의 귀속 규칙으로 계산한다. 월 예상 소비액의 80% 도달은 주의, 100% 초과는 위험이다. 변경 작업이 100% 초과를 발생시키면 저장/확정 전에 확인하되 적용 예산이 0이면 확인하지 않는다.

### 5.3 예정 지출 결제·환불

1. 사용자는 예정 지출의 정가, 일반 할인, 포인트 할인, 사용 포인트, 포인트 플랫폼, 실제 결제수단, 자산 차감 여부 및 결제일을 입력한다.
2. UI는 입력 범위와 최종 확인을 돕지만 최종 금액/포인트 적립을 권위 있게 결정하지 않는다. 저장된 합계 증가가 예산 초과를 일으키면 먼저 확인을 받는다.
3. 확인 후 `process_expense_payment`를 호출한다. DB는 소유자·상태·금액·스토어 정책·포인트 잔액·KST 미래 날짜를 검증하고 원자적으로 변경한다.
4. 성공 시 관련 지출/자산/지갑/원장/월 집계를 재조회한다. 실패 시 기존 상태를 유지하고 오류를 알린다.
5. 환불은 별도 확인 후 `refund_expense_payment`를 호출한다. 포인트 적립분을 이미 사용해 회수할 수 없으면 서버가 전체 작업을 거부하고 화면은 결제가 확정 상태로 남아 있음을 표시한다.

### 5.4 반복 구독, 일정 승인 및 예정 만료

- 캘린더 월 데이터를 준비할 때 활성 구독 템플릿의 누락된 월별 회차만 생성한다. `(template_id, billing_cycle)` 유니크 인덱스 충돌은 동시 요청의 중복 생성을 막는 멱등성 경계다. 취소 회차를 자동 재생성하지 않는다.
- 템플릿 비활성화는 DB 트리거가 연결된 미결제 회차를 `TEMPLATE_DEACTIVATION` 취소로 보존한다. 재활성화는 과거 회차를 자동 복구하지 않는다.
- 일반 사용자의 게임/일정 변경은 요청 행을 만든다. 관리자 승인 RPC는 승인된 공용 행과 요청 상태를 한 트랜잭션에서 변경한다.
- 온라인 복귀 시 KST 오늘보다 목표일이 지난 `PLANNED` 지출을 다시 조회해 필수 처리 모달을 연다. 사용자는 결제 확정, 취소 또는 다음 가능한 일정으로 이동해야 캘린더 상호작용을 계속할 수 있다. 오프라인에서는 모달을 닫을 수 있으며, 미해결 항목은 다음 온라인 복귀 때 다시 확인한다.

### 5.5 계정 삭제 요청

1. 사용자가 영향 설명을 확인하고 삭제를 요청하면 권한 있는 서버 경로가 내구성 있는 삭제 작업을 만든다. 계정은 `PENDING_DELETION` 상태가 되고 일반 개인 기능/데이터 접근을 RLS 또는 동등한 서버 경계에서 차단한다. 세션은 유지해 상태 화면을 볼 수 있게 한다.
2. 작업자는 사용자별 비공개 아이콘을 정리하고 계정 삭제 대상 개인 데이터를 제거한다. 일시 실패 시 작업 상태를 유지하고 재시도 간격을 늘려 자동 재시도한다. 로그아웃/다른 탭을 포함해 일반 기능 접근이 열리지 않는지 검증한다.
3. 데이터 및 Storage 정리가 성공한 후, Auth 계정이 아직 존재할 때 등록 이메일로 “개인 데이터/Storage 정리 완료, 계정 삭제 마무리 중” 안내를 보내고 발송 성공을 작업에 기록한다. 이메일 주소를 별도 복사해 저장하지 않는다.
4. 이메일 발송 성공 뒤 Auth 계정을 마지막으로 삭제한다. 삭제가 성공한 경우에만 삭제 작업을 완료로 처리하고, 열린 클라이언트는 완료 화면 후 로컬 세션/캐시를 제거한다.
5. 메일이 수락된 뒤 Auth 삭제가 실패하는 경우 중복 알림을 보내지 않도록 발송 상태를 보존하고 Auth 삭제만 재시도한다. 이 동안 상태 화면도 계정 마무리 중임을 표시한다.

### 5.6 게임 구독 해제와 아이콘 정리

1. 사용자가 내 게임 목록에서 구독 해제를 요청하면 Storage 객체를 정리하는 내구성 있는 작업을 만든다.
2. 객체 삭제가 일시 실패하면 작업을 유지하고 재시도 간격을 늘려 서버가 재시도한다. Storage 객체가 아직 정리되지 않은 동안 `user_games` 행은 유지한다.
3. 아이콘 정리가 성공한 뒤에만 `user_games` 행을 제거하고 구독 해제 완료를 알린다. 삭제 작업이 완료될 때까지 중복 요청은 멱등하게 처리한다.
4. 정리 대기 중에는 게임을 목록에 유지하고 “삭제 처리 중”으로 표시하며 중복 해제 동작을 막는다. 작업 상태와 재시도 구조는 계정 삭제 작업과 같은 신뢰된 서버 실행 경계가 필요하다.

## 6. UI 및 접근성 계약

- 화면 시각 방향은 [UI Design Sheet](../md/ChronoLedger_UI_Design_Sheet.md)를 참고한다. `[PROPOSED]` 색상·글꼴·간격·브레이크포인트는 SRS 요구사항이 아니므로 사용자 확정 전 고정 사양으로 취급하지 않는다.
- 로그인은 `/auth` 단일 화면에서 이메일/비밀번호와 Google 인증을 제공한다. 현재 앱의 다크 테마에 맞추며 입력 레이블과 명시적 버튼을 사용한다. 앱 전체 테마 전환은 로그인과 보호 화면을 함께 적용하는 후속 작업이다.
- 데스크톱은 캘린더와 상세 사이드바, 모바일은 캘린더와 상세 바텀 시트를 기본 구조로 한다.
- 비동기 데이터 조회에는 로딩/오류/빈 상태를 구분한다. 실제 0원과 조회 실패를 같은 값으로 표시하지 않는다.
- 모든 파괴적/회계 영향 동작은 실행 전 영향과 확인을 표시하고, RPC 실패 시 성공 토스트나 낙관적 최종 상태를 유지하지 않는다.
- 상태 색상만으로 상태를 전달하지 않고 텍스트/레이블을 함께 사용한다. 키보드 포커스, 입력 레이블, dialog 닫기/복귀는 구현 테스트 대상이며 구체적 WCAG 목표는 아직 승인되지 않았다.

## 7. 보안·개인정보 경계

- 브라우저 번들에는 Supabase anon/public key만 둔다. service-role key 또는 OAuth client secret을 넣지 않는다.
- DB RLS는 사용자별 행 격리, RPC는 인증/소유권/상태/금액 검증의 최종 경계다. `SECURITY DEFINER` 경로는 스키마에서 정한 실행 권한 및 고정 `search_path` 설정을 유지한다.
- 지갑, 원장, 확정 결제 상태는 직접 table write로 바꾸지 않는다. 클라이언트는 관리 역할이나 사용자 ID를 입력해 권한을 상승할 수 없다.
- Storage bucket은 private이며 인증된 소유자 경로에만 접근한다. 이미지 입력은 원본 5 MiB 이하와 허용 MIME을 확인하고, 256×256 WebP 결과가 100 KiB 이하여야 한다.
- 요청 오류에는 사용자가 조치할 수 있는 메시지만 표시한다. SQL 상세, 세션 토큰, 비밀값, 다른 사용자 데이터를 오류/로그에 노출하지 않는다.
- 오프라인 캐시는 유효한 인증 세션에서만 읽고 쓰기 큐를 두지 않는다. 로그아웃/만료 때 개인 캐시는 표시하지 않는다. 실제 캐시 저장소와 제거 전략은 §10 미결정 항목이다.

## 8. 오류 및 복구 정책

| 오류 경계 | 사용자 동작 |
|---|---|
| 인증 취소/공급자 오류/PKCE 교환 실패 | callback에서 원인을 짧게 알리고 로그인 화면에서 다시 시도할 수 있게 한다. 세션이 없는 상태로 보호 화면에 진입하지 않는다. |
| RLS/소유권/관리자 권한 거부 | 요청을 거부하고 권한 없음 상태를 표시한다. 다른 사용자의 데이터로 폴백하지 않는다. |
| 잘못된 금액/플랫폼/상태 전이 | 기존 DB 상태를 유지하고 수정 가능한 입력 오류 또는 작업 불가 안내를 제공한다. |
| 잔액 부족/환불 포인트 회수 불가 | 회계 작업 전체가 롤백된 상태를 표시하고, 지출/잔액의 일부 성공으로 보여주지 않는다. |
| 네트워크 오류 | 조회 오류와 정상 빈 결과를 구분한다. 오프라인 허용 범위의 읽기만 세션 정책에 따라 제공하고 지출 쓰기는 비활성화한다. |
| Storage 변환/업로드/삭제 실패 | 이미지 저장 또는 게임 제거가 완료된 것처럼 표시하지 않는다. 재시도 방법을 안내하고 DB/Storage 사이의 정리 원칙은 §10에서 확정한다. |

## 9. 검증 설계 및 추적성

구현 시 각 케이스에 자동/수동 여부, fixture, 기대 결과, 실행 환경, 결과를 기록한다. 아래는 요구사항 그룹별 최소 검증 계획이며 전체 목록은 릴리스 테스트에서 상세화한다.

|---|---|---|
| 가입/인증 (FR-001, FR-005) | 가입 초기 재무·두 지갑 생성; 이메일 인증; Google PKCE 성공/취소/오류; 로그아웃·만료 후 캐시 비노출 | DB smoke test + 브라우저/PWA 통합 |

| 예산/캘린더 (FR-020–022) | 종료일 월 귀속, 확정일 월 귀속, 취소 제외; 월 예산 0/누락 fallback; 80%/100% 경계; 일정 범위/메모 도트 | 순수 함수 단위 + 화면 통합 |
| 결제/환불 (FR-030–045, NFR-002–003) | 할인 합계·0원 경계; 자산 차감/비차감; 포인트 사용·적립; wallet 결제 미적립; 미래 KST 날짜 거부; 부분 변경 없는 실패; 적립분 부족 환불 거부 | RPC SQL 통합 + 입력 UI 테스트 |
| 구독/만료 (FR-050–063, NFR-005–006) | 월말 보정; 동시/반복 lazy generation; 취소 월 중복 방지; 템플릿 비활성화·복구; 온라인 복귀 후 만료 재처리 | 함수 단위 + DB concurrency/통합 |
| 파일/메모 (FR-070–072, NFR-004) | 아이콘 MIME/크기/변환 경계, 타 사용자 Storage 접근 거부, 게임 제거 시 아이콘 정리, 여러 메모/한 도트 | 변환 단위 + Storage 통합 + 화면 테스트 |
| 비기능/배포 | 모바일 반응형, 접근성 기본 동작, 느린/끊긴 네트워크, SRS 플랫폼의 설치/패키징 및 성능 측정 | 앱 릴리스 버전/시점 결정 후 실기기 검증; 배포 플랫폼 및 Netlify/Web·Desktop 분리 제안은 별도 결정 |

`md/TESTS.sql`은 이미 배포된 스키마를 대상으로 하는 rollback-only smoke suite다. 전체 SRS 수용 검증의 일부이며 production 배포 증거나 전체 회귀 테스트로 간주하지 않는다. 전체 계정 삭제와 Storage 정리, Android PWA/Windows Tauri v2 주요 흐름 및 성능 수치는 아직 별도 검증이 필요하다.
